## 1. 목표와 자료 사용법

사용자는 새 4차 디자인으로 UI를 다시 구현하고, 구현은 Work에서 진행한다. 이번 작업은 기존 C안의 색상·여백만 보정하는 것이 아니다.

> **왼쪽: 공장·시스템과 업무 탐색 / 가운데: 업무 수행 / 오른쪽: 실제 Native EES Assistant**

UI 배치·컴포넌트·스타일은 필요한 범위에서 새로 구성한다. 이미 있는 인증·권한·업무 데이터·저장·실행·판정·대화 기능은 재사용한다. 기존 배치를 보존한다는 이유로 중앙 대화·오른쪽 업무 화면으로 돌아가지 않는다. 반대로 화면 재구현을 백엔드·채팅·실행기 전체 재작성으로 확대하지 않는다.

## 3. 시작과 재사용 경계

1. 최신 main·관련 열린 PR·로컬 변경·기존 검사 결과를 먼저 확인한다. main과 실제 작업 PR head의 `AGENTS.md`, `docs/STATUS.md`를 읽는다. 같은 목적의 진행 PR은 재사용하고, 없으면 최신 main에서 분기한다. 다른 로컬 변경을 초기화하거나 혼합하지 않는다.
2. `README.md` 지도에서 필요한 코드와 테스트를 찾고 `docs/mockups/ees-work/TASK.md`, `docs/03-openwebui-native-agent.md`, `evals/scenarios.md`와 관련 평가 기록을 확인한다. 반복된 외형 불일치·Native 보내기·저장/실행/복귀 실패의 교훈을 이번 검사에 연결한다.
3. ‘새 UI 요소 / 기존 컴포넌트·서비스·데이터 / 변경할 연결 / 검사 / 미지원’ 대응표를 짧게 작성한다. UI의 필요한 연결 코드는 구현하되, 기존 코드를 실제로 확인하지 않고 “기존 기능을 쓰면 됨”으로 끝내지 않는다.
4. 이전 대화의 main 참고점은 `b0515d594da36112919a14c814a95e2b5900035e`다. 이번 문서 작성에서 Git을 재조회한 값이 아니며 checkout 고정 지시가 아니다. #66/#67의 기존 기능·당시 증거는 보존하고 종료된 C안 작업을 재개하지 않는다. Draft #53을 임의로 병합·적층하지 않는다.

다음 기능은 재사용·회귀 확인 대상이다. PDF 작성자도 실제 커스터마이징 범위를 확인하지 못했다고 명시했으므로(PDF 8장, 11쪽), 현재 지원 여부는 Work가 코드에서 확인한다.

| 영역 | 보존·재사용 범위 |
|---|---|
| Native 대화 | 기존/새 대화 ID·메시지 저장, 실제 보내기·첨부·스트리밍·중지·재생성, 모델/도구/스킬 선택, 대화 기록 |
| 계정·권한 | 기존 로그인·가입·승인·그룹, 업무 이용/절차 관리/플랫폼 관리, 시스템 담당 권한, P별 게시 |
| 업무·실행 | 기존 절차/진행 건/P/T/J/run 식별자, 입력 schema·저장·판정·실행 당시 snapshot·기록, 기존 P/T 실행 및 복귀 |
| 사용자 자산 | Git에 없는 Skill·Tool·Prompt·모델·Knowledge·연결 정보·개인 설정, 개인 PAT와 ACL |
| 운영 | 기존 DB·키, Native 커스터마이징·빌드·래퍼 적용/복원 경로, 기존 프로그램과 자료의 호환 경계 |

새 채팅·별도 LLM 루프·인증·DB·공용 PAT·독립 실행기·프런트엔드 프레임워크를 만들지 않는다. Open WebUI/Hermes 업그레이드, 운영 DB 직접 접근, DML/DDL, 승인되지 않은 네트워크 우회는 범위 밖이다. DB 조회는 승인된 읽기 전용 API/Query Broker만 사용한다.

Git에 없는 자산을 미사용으로 판단해 삭제·초기화·재등록·일괄 동기화하지 않는다. 새 화면이 보이지 않는다는 이유로 기존 사용자 패널 폭·닫힘·대화 설정을 초기화하지 않는다. 필요한 UI 설정 호환 처리는 영향을 확인하고 기록한다.

## 4. 화면 구현 범위

세부 색값·치수는 PDF 3~6장의 표를 읽고 적용한다. 이 인계서에서 전부 복제하지 않는다.

### 4.1 공통 셸과 왼쪽 탐색

1920 기본값은 사이드바 256 / 중앙 가변(기준 1304) / Assistant 360, 상단 바 48, 중앙 기본 좌우 여백 32다. J 상세에서는 **중앙 내부**를 본문 가변(기준 1004) + 정보 칸 300으로 나눈다. 목록→상세는 같은 중앙 자리에서 전환하고 별도 상설 전역 패널을 더 만들지 않는다.

평평한 면·1px 구분선·v4 선택색을 사용한다. 떠 있는 카드·그림자·그라데이션·보라색 AI 연출·불필요한 알약형 태그를 추가하지 않는다. PDF의 명사형·‘~합니다’ 문구를 유지한다. 이전 스타일 위에 무관한 전역 CSS를 계속 누적하거나 다른 Native Workspace·관리 화면을 훼손하지 않는다.

왼쪽은 제품명 → 작업 공간 선택 → 내 업무/워크플로우 찾기/실행 기록/대화 기록 → 업무 분류 → 워크플로우 → 단계 → 계정이다. 개별 J 전체를 왼쪽 트리에 다시 나열하지 않는다. 선택과 펼치기, 상위 단계 선택과 현재 J 상세의 경로를 일치시킨다. 긴 이름은 키보드에서도 전체를 확인할 수 있어야 한다.

PDF 용어를 따른다: 작업 공간=공장+시스템, 절차=게시 가능한 반복 틀, 워크플로우=이번 진행 건, 단계=T, 작업=J, 실행=run, 실행 기록=읽기 전용 snapshot. 이 용어 적용을 저장 ID·schema 변경으로 확대하지 않는다. 공장·시스템의 ‘작업 공간’과 Native 자산 관리 메뉴 ‘Workspace’를 같은 저장소/권한이라고 가정하지 않는다.

### 4.2 작업 목록 — 4차 A

단계 머리·진척·일정/담당/절차 버전, 검색·담당 필터·정렬, 상태별 표를 구성한다. 열은 상태 / 순서 / 작업 / 수행 방식 / 담당 / 후속 작업 / 최근 실행 / 행동이며 PDF의 폭·행 높이·글자 스타일을 따른다.

할 일 → 진행 중 → 대기 → 완료 순서와 기본 펼침 상태는 PDF 6장을 따른다. 대기는 앞 2행과 더 보기, 완료는 기본 접힘, 0개 묶음은 숨김이다. 실패·판정 미확인을 단순 대기로 바꾸지 않는다. 행 전체와 행 안의 행동 버튼은 실제 상세/행동에 연결하고 이벤트 중복을 막는다.

권장 정렬은 PDF 7장의 **임시 규칙**(선행 충족 미완료 → 후속 미완료 작업 수 내림차순 → 절차 순서)을 출발점으로 삼는다. 긴급도 필드를 새로 만들거나 렌더링마다 LLM이 순서를 정하게 하지 않는다. ‘먼저’는 후보가 있을 때 1개뿐이며 실행 권한이나 승인 대체가 아니다. 담당 필터와의 관계·최종 계산식은 PDF 10장의 미결정으로 남긴다. 기존 의존 모델로 확정할 수 없는 후속 집계 범위를 추측하지 않는다.

작업 번호는 표시용이며 안정적인 ID가 아니다. 번호의 인접성만으로 선행·병렬 관계를 만들지 않는다. 집계·담당자·시간·HTTP 코드·도구 수는 실제 데이터에서 표시한다. Figma의 73/120과 하위 합계 18+21+25+8=72가 같은 집계라면 일치하지 않으므로, 일관된 합성 fixture를 사용하고 숫자 차이를 명시한다. 잘못된 예시 숫자를 하드코딩해 시각 검사를 통과시키지 않는다.

### 4.3 작업 상세 — 4차 B

제목·상태·ID/수행 방식·진행 표시, schema 기반 입력, 확인 항목/완료 기준, 기록, 중앙 내부 정보 칸과 하단 단일 행동 영역을 구현한다. DB 연결 확인 전용 폼·고정 결과로 범용 J를 대체하지 않는다.

PDF의 ‘입력→점검→판정’은 DB 예시의 화면 흐름이다. 새 저장 계층을 만들지 않으며, 다른 지원 J에는 실제 기능에 맞는 입력·행동·결과 이름을 사용한다. 기존 schema를 한 개 text 입력으로 축소하거나 표시되지 않는 값을 버리지 않는다.

정보 칸의 상태·담당·순서·병렬 여부·선행/후속·절차와 접힌 기술 정보는 기존 데이터/자산에 연결한다. 정보가 없다는 사실, 조회 실패, 권한 없음은 서로 다르게 취급한다. 실제 지원되지 않는 공동 진행·담당 필드를 표시하기 위해 새 다중 사용자 백엔드를 만들지 않는다.

### 4.4 원안에 없는 화면과 기존 기능

실행 중·실패·판정 미확인·결과/기록·사람 확인은 미설계이지만 핵심 왕복 동작에 필요하다. 기존 컴포넌트와 PDF 동작 규칙으로 연결하고, 별도 v4 프레임과 일치한다고 주장하지 않는다.

기존에 지원되는 P/T 관리·공통 실행, 절차 보기/작성/검토/게시, 운영·장애대응, 내 업무·탐색·기록·설정 접근은 보존한다. 대표 두 화면이 없다는 이유로 삭제하거나 빈 화면으로 바꾸지 않는다. 새 전체 대시보드·작성기·신규 업무 도구 개발은 범위 밖이다. 기존 기능의 최소 스타일 정합화와 새 전용 화면 디자인을 구분한다.

## 5. 반드시 연결할 동작

### 5.1 상태 — PDF 7장, 8~9쪽

| 화면 상태 | 기호 | 묶음 | 허용 행동의 기본 기준 |
|---|---|---|---|
| 입력 필요 | Action | 할 일 | 입력·저장 |
| 검토·확인·승인 필요 | Action | 할 일 | 현재 권한과 절차에 따른 검토·확인·승인 |
| 실행 가능 | Action | 할 일 | 점검 시작. 기본값 실행 등 기존 계약의 예외는 유지 |
| 선행 대기 | Waiting | 대기 | 보기만 |
| 실행 중 | Running | 진행 중 | 보기, 중복 실행 금지 |
| 실패 | Failed | 할 일 | 결과 보기·대상 확인 후 명시적 재점검 |
| 판정 미확인 | Unknown | 할 일 | **상태 다시 조회, 새 실행 금지** |
| 완료 | Done | 완료 | 기록 보기 |

이 표는 화면 대응표이며 기존 상태 enum을 축소하는 지시가 아니다. 기존 상태와 대응이 다르면 근거를 기록한다. 특히 판정 미확인을 실패와 합쳐 자동 재시도하지 않는다. 부분 결과의 새 기호·묶음·행동은 미결정이며 기존 결과를 보존하되 성공/완료로 임의 분류하지 않는다.

HTTP 성공·도구 호출 성공·AI의 성공 문장은 업무 완료가 아니다. 검증된 완료 기준과 실제 결과로 판정한다. J 완료는 P/T 집계를 갱신할 뿐 상위 전체 완료를 의미하지 않는다. 상태는 색·모양·문구로 구분한다.

### 5.2 초안·저장·실행과 결합 버튼

작성 중 초안 / 서버 저장값 / 실행 당시 불변 snapshot을 분리한다. AI가 채운 값은 초안이며 저장·실행이 아니다. 유효한 값이 채워졌는지, 검토가 필요한지, 저장됐는지를 구분한다. AI가 값을 채운 뒤 이유 없이 ‘입력 필요’를 남기지 않는다.

작업을 옮겼다가 돌아와도 초안을 잃지 않는다(PDF 7장). 이 요구를 임의의 새 서버 저장·자동 저장으로 구현하지 않는다. 기존 초안/화면 상태 경로를 우선 사용하고, 새로고침 이후 **미저장 초안**까지 보장하는지는 현재 지원 범위와 구분한다. 저장된 입력의 재접속 복원은 실제 서버 저장으로 확인한다.

‘저장’은 저장만 한다. ‘저장하고 점검’은 H-03의 조건부다. 허용되는 작업에서는 유효성·현재 권한 확인 → 조건부 저장 성공 → 저장된 입력/snapshot에 대한 기존 실행 요청과 승인 절차 순서를 보장한다. 저장 실패·충돌·권한 거절이면 실행 0회다. 승인 대기까지를 실제 점검 시작으로 표시하지 않는다.

기존 계약으로 저장 버전과 실행 대상·승인을 연결할 수 없다면 ‘저장’과 ‘점검 시작’을 분리하고 이유를 기록한다. 모든 J에 저장 선행을 강제하지 않는다. 결합 버튼 외형을 위해 새 큐·트랜잭션·실행 엔진을 만들지 않는다.

연속 클릭·응답 지연·재렌더링으로 중복 실행되지 않게 기존 중복 방지 계약을 사용한다. 편집 중 값과 이미 시작한 실행값을 섞지 않는다. 재점검은 명시적 새 시도이며 과거 실패를 덮어쓰지 않는다. 화면을 닫아도 실행이 취소됐다고 추측하지 않는다.

### 5.3 Native Assistant와 입력 도움

오른쪽에는 기존 실제 Native 대화를 배치한다. 새 말풍선 HTML·가짜 ActionRecord·별도 메시지 저장소로 대체하지 않는다. 현재 지원되는 보내기·첨부·모델/도구·스트리밍·중지·기록과 Workspace 접근을 유지한다.

대표 흐름은 실제 Native 요청 → 허용된 자료/도구 조회 → 대상 J의 초안 변경 → 업무 화면의 AI 표시·근거·되돌리기와 대화 ActionRecord 갱신이다. 실제 필드 반영이 확인돼야 ‘입력함’으로 표시한다. API/권한/필드 검증을 건너뛴 DOM 변경만으로 업무 변경 성공을 주장하지 않는다. 필요한 UI-action 연결은 기존 서비스·권한 경로 안에서 구현한다.

AI는 설명 요청을 실행 요청으로 바꾸지 않는다. 직접 조작은 AI 응답을 기다리지 않고 완결돼야 하며, 같은 업무 행동은 채팅과 버튼에서 같은 서비스·검증·권한을 사용한다. 미구현된 연결이 있으면 더미로 대신하지 말고 핵심 차단인지 구분한다.

되돌리기는 **해당 AI 변경 직전의 초안** 범위다. 두 화면의 표시를 함께 갱신하되 이후 사용자 수정·다른 저장 버전을 과거 값으로 덮지 않는다. 안전하게 되돌릴 수 없는 경우 이유를 보여준다. 저장·실행 자체를 취소하거나 과거 기록을 삭제하는 기능으로 확대하지 않는다.

### 5.4 참고 대상·과거 메시지·실행 대상

PDF 7장(10쪽)의 세 대상을 분리한다: 다음 질문의 참고(ReferenceTag), 메시지별 당시 참고, 실행 서비스가 검증한 작업·진행 건·입력 snapshot. 화면 전환으로 이전 메시지의 참고나 실행 대상을 바꾸지 않는다.

화면을 옮겨도 대화·미전송 글·첨부·진행 중 스트림은 유지한다. ReferenceTag 해제는 일반 대화이며 과거 기록 삭제가 아니다. 과거 실행을 참고로 열어도 현재 입력·실행·판정은 바뀌지 않는다. 비동기 응답/입력 반영이 다른 J에 잘못 적용되지 않게 대상 ID와 버전을 확인한다.

추천 질문은 실제 현재 상태에서 만들고 PDF 명세대로 누르면 전송된다. 이미 작성 중인 글·첨부가 있는 경우는 기존 Native 동작과 보호 규칙을 확인하며 임의 폐기·이중 전송하지 않는다.

### 5.5 조회 실패·권한·과거 기록

자료 조회 실패 시 이전 입력·결과를 상세 본문에서 숨긴다. 원인을 연결 장애·권한 문제로 단정하지 않는다. 초안을 보존하는 것과 권한 확인 없이 다시 표시하는 것은 다르다(H-04). 업무 상세와 대화 기록의 접근 정책을 각각 적용한다.

과거 실행은 읽기 전용이며 그 화면에 재실행 버튼을 두지 않는다. 현재 작업에서 대상을 확인한 후 재점검하는 경로와 구분한다. 기록 열람·절차 편집/게시로 진행 중인 건과 과거 snapshot·집계를 조용히 바꾸지 않는다.

모의 / 실제 읽기 전용 조회 / 미연결을 목록·상세·결과·기록에서 사실대로 구분한다. ‘실제 시스템 변경 없음’만으로 모의와 읽기 전용 조회를 혼동시키지 않는다. 모의 통과를 실제 점검 성공으로 집계하지 않는다. 합성 진행 건의 진행률은 해당 범위임을 명시한다.

### 5.6 목록 복귀·키보드

목록→상세→기록→목록에서 검색·담당 필터·정렬·묶음 펼침·스크롤·열었던 행의 초점을 보존한다. 완료 시 해당 작업은 완료 묶음으로 옮기고 필터를 해제하지 않는다. PDF의 완료 이동 안내와 다음 할 일 초점을 기존 안내/초점 컴포넌트로 연결한다. 다음 행이 없으면 기존 안전한 초점 복귀 규칙을 사용한다.

Enter 전송 / Shift+Enter 줄바꿈 / IME 조합 중 Enter 전송 금지 / Esc 메뉴 닫기 / 사이드바→메인→Assistant Tab 순서 / 행 Enter로 상세 열기 / 가시 포커스를 확인한다. 행 내부 버튼으로 인해 상세 열기·실행이 이중 발생하지 않도록 한다.

## 6. 스타일 자산·반응형

PDF 4장의 CSS 변수와 의미 토큰을 사용하고 색값을 개별 컴포넌트마다 중복 하드코딩하지 않는다. 적용 범위를 EES 화면에 한정한다. PDF 5~6쪽의 서체·행간·굵기, 6쪽 컴포넌트, 상태 기호 6종과 화면 상태 8종을 구분해 구현한다.

PDF는 Figma의 Noto Sans KR/Inter와 구현용 Pretendard 우선·Noto Sans KR 대체를 구분한다. 기존 로컬 자산과 배포 가능 출처를 확인하고 실제 적용 서체·fallback을 기록한다. 서체가 다르면 줄바꿈·폭 차이도 대조한다. 글꼴·아이콘을 외부 CDN에 의존시키지 않는다. 숫자 `tabular-nums`, 지정 포커스, 한 영역당 Primary 하나를 적용한다. 묶음에 글꼴 파일은 포함하지 않는다.

PDF 3장의 임시 반응형: 1536px 이상 기본 폭 / 1280~1535px 사이드바 224·Assistant 320 / 1280 미만 Assistant 덮개 패널. 열고 닫을 때 대화·글·첨부를 유지한다. 사이드바 접힘의 새 전용 디자인은 미설계이므로 기존 접근 가능한 컴포넌트를 재사용한다.

Assistant 입력창은 viewport에 비례해 늘리지 않고 내용에 따라 최대 6줄, 이후 내부 스크롤한다. 1920 기본 배치의 정보 칸 300·입력 440을 모든 화면에 무조건 고정하지 않는다. 좁은 본문에서는 기존 반응형 입력·표·패널 기능으로 핵심 내용과 주 행동의 접근을 보장하고 의도된 차이를 기록한다. 1920 정보 칸 통합이나 행동 바 이동으로 확대하지 않는다.

기존 사용자의 폭·접힘 설정과 새 기본 설정을 각각 검사한다. 새 기본 설정의 시각 대조를 위해 실제 사용자 설정을 초기화하지 않는다. 다크는 H-06 범위만 검사한다.

## 7. 남겨둘 결정과 범위 제한

PDF 10장(12~13쪽)을 원본으로 두고 관련 항목만 기존 TASK/STATUS에 연결한다. 미결정을 사전 승인으로 바꾸거나 같은 사실을 여러 표에서 독립 관리하지 않는다.

| 항목 | 이번 작업에서의 처리 |
|---|---|
| 저장하고 점검 | 기존 계약 확인 후 결합/분리. 허용 여부·근거와 선택 결과를 보고 |
| 분류 옆 숫자 | 현재 시안인 ‘진행 중인 워크플로우 수’를 사용. ‘할 일 수’로 변경하지 않음 |
| 권장 순서·담당 필터 | PDF 임시 규칙으로 구현 가능한 범위를 표시. 최종 계산식·필터 관계는 미확정임을 남김. 합성 fixture에서 사용한 필터 범위를 명시 |
| 부분 결과 | 기존 결과·상태를 유지. 새 기호·완료 처리·허용 행동을 임의 확정하지 않음 |
| 목록 미저장 초안 표시 | 현재 없는 새 뱃지를 임의 추가하지 않음. 초안 보존과 상세의 미저장 표시는 구현 |
| 미설계 상태/화면 | 필수 왕복은 기존 컴포넌트로 실제 연결. 남은 전용 디자인만 TODO로 표시 |
| 전체 진행·절차 작성/게시·다른 분류 | 기존 지원 기능과 접근 보존. 새 전용 화면·기능 개발로 확장하지 않음 |
| 반응형·다크 | 임시 반응형 검증과 기존 다크 보존. 새로운 확정 디자인으로 보고하지 않음 |
| 실제 데이터/서비스 부재 | 미등록·미지원·조회 실패를 구분. 사실을 꾸미거나 새로운 협업 모델로 보충하지 않음 |

큰 제품 판단이 필요하면 대상·선택지·영향을 구체적으로 묶어 남긴다. 이미 명세가 있는 나머지 구현은 계속 진행한다. 핵심 연결이 막히면 부분 완료 범위를 명시하고 전체 완료로 보고하지 않는다.

## 8. 구현 순서와 수락 기준

### 8.1 같은 구현 PR 안의 세 단계

**1단계: 실제 제품 셸과 대표 왕복.** Figma/PDF 기준 확보·재사용 대응표·영향 검토 후 실제 Native 앱에서 목록→상세→입력/초안→저장→허용된 실행→판정/기록→목록 복귀와 Assistant 입력 도움을 연결한다. 이때부터 실제 빌드 산출물로 렌더링한다. 별도 HTML 목업을 만든 뒤 제품 연결을 미루지 않는다.

**2단계: 공통 J와 기존 경로 보존.** DB 외 기존 지원 schema/사람 작업, 실패·판정 미확인·조회 실패·권한/충돌·과거 기록을 연결한다. 기존 P/T 실행·관리·절차 작성/게시·Native Workspace 접근을 보존한다. 동작 연결이 없는 외형만으로 통과시키지 않는다.

**3단계: 실제 제품 대조·회귀·마감.** 아래 필수 검사를 수행하고 관련 결함을 수정한 뒤 같은 조건으로 재검한다. 문서·커밋·push·Draft PR까지 끝낸다. 단계마다 중복 PR을 만들거나 같은 승인을 반복해서 묻지 않는다. 단, 실제 도구 권한 제한과 이번 병합·배포 제외는 유지한다.

1920 A/B는 같은 viewport·테마·서체/설정·상태·합성 데이터로 원안과 대조한다. 나란히 보기/겹침·주요 좌표·computed style로 큰 차이를 확인한다. 단순 PNG 생성이나 파일명 일치가 시각 검수 통과는 아니다. 합성 수치 정합성·실제 schema·안전상 버튼 분리 등 정당한 차이는 별도 기록하고, 외형 차이를 가려 통과시키지 않는다.

작은 화면은 PDF의 1536×960·1366×768 및 이전 인계의 1440×900, 큰 화면은 2560×1440을 배치 점검한다. 덮개 분기 확인용 1200×800은 **이번 인계서가 추가한 검사 크기**이며 확정 디자인이 아니다. 모든 기능을 모든 크기에서 반복하지 말고, 긴 작업명·넓은 표·긴 답변·입력·행동 바 등 위험한 상태를 골라 resize/초점/넘침을 확인한다.

PDF가 주장한 글자 대비와 토큰 수치만으로 접근성 PASS를 선언하지 말고 실제 글자·바탕 조합과 초점을 확인한다. 기본/hover/disabled와 사용자 설정을 구분한다. 실제 사용자 검토를 하지 않았다면 ‘처음 쓰는 사람 사용성 검증 완료’라고 보고하지 않는다.

### 8.3 검사 종류와 차단 범위

코드/자동시험, **실제 Native 앱+합성 데이터의 제품 통합 검사**, Figma 시각 대조, 실제 모델/API, 디자이너 검토, 실제 사내/사용자 확인을 분리한다. 합성 테스트 도구를 기존 실행 서비스로 호출한 검사와 실제 사내 DB 접속은 다른 증거다. 정적 응답·상태 주입·대체 채팅으로 실제 모델 호출/실행 성공을 주장하지 않는다.

과거 PASS는 영향이 없는 범위에서 재사용한다. 이번 배치 변경이 직접 영향을 주는 Native 입력·보내기·스크롤·초점·복귀·실행 행동은 실제로 다시 확인한다. 실패 후 수정한 대상은 동일 조건으로 재검하며 최초 실패·미해결도 남긴다.

PDF 2장에 따라 Figma 접근 불가 시 PDF 수치로 가능한 구현은 진행할 수 있다. 다만 design context·기준 이미지·실제 대조가 미확인임을 표시하고 원안 일치 PASS를 선언하지 않는다. `HTTP 400 / Invalid MCP request metadata`가 재발하면 실패 도구·오류를 기록하고 같은 호출 반복·재연결/키 변경·사내 서버 조치를 요구하지 않는다. 이용 가능한 기준으로 진행할 수 없는 부분만 차단 범위를 명시한다.

## 9. 문서·Git·최종 보고

기존 `TASK.md`, `docs/STATUS.md`, 관련 `evals/` 기록, `CHANGELOG.md`를 갱신한다. 이 문서의 적용 규칙은 TASK의 새 4차 절에서 관리하거나 연결한다. PDF 토큰·미결정 표를 여러 문서에 복제하지 않는다. 이전 C안 기준·실패·기능 증거는 날짜가 있는 과거 기록으로 보존한다.

관련 자동시험, `python scripts/check_docs.py`, `git diff --check`를 실제 실행한다. 기존 확인된 개발 환경을 재사용하고 사내 PC의 환경 준비로 확대하지 않는다. 미실행 명령·플랫폼과 제품 결함을 구분한다.

실제 작업 날짜와 최신 STATUS의 CI 방침을 다시 확인한다. 이전 지시의 2026-09-30까지 커밋별 `[skip ci]`는 참고이며, 2026-10-01 이후에도 이 인계서만 보고 생략을 연장하지 않는다. 최신 재개 기준을 따르고 무관한 결제·보호 설정·예약 실행을 만들지 않는다.

구현·관련 문서·검사를 마친 뒤 feature branch에 커밋·push하고 동일 작업 Draft PR을 생성/갱신한다. main 직접 push·강제 push·보호 우회·병합·Draft 해제·사내 적용은 하지 않는다. 검토 스크린샷/증거와 설치용 배포물을 구분하며 반복적인 배포 ZIP 생성을 작업의 선행조건으로 추가하지 않는다.

최종 보고에는 다음을 구분한다.

1. 실제 변경 화면·재사용 서비스, PR·브랜치·head.
2. 실제 제품 A/B와 원안 대조 결과, 의도된 차이·아직 남은 외형 차이.
3. 저장/실행/판정/Native/보존 검사, 발견한 관련 결함과 동일 조건 재검 결과.
4. PDF 미결정의 처리 결과·아직 필요한 결정, 차단·미실행과 재개 위치.
5. 이번에는 병합·배포·Figma 원본 변경을 하지 않은 상태.
