## 화면 확인 방법

PR의 최신 EES delivery 실행에서 `ees-work-browser-evidence-native-compose`를 내려받아 압축을 풀고 `ees-results/figma-review/index.html`을 연다. 8개 화면의 1104×1080 피그마 업무 영역과 1920×1080 제품 캡처 중 같은 영역을 나란히 표시한다. 원본 PNG와 DOM 실측도 함께 들어 있다. ‘상태별 전체 캡처’에는 A4-2·B4·480px 회차 상세·T07 등의 동작 결과가 있다. 파일이 없으면 해당 화면은 미확인이다.

변경 전까지 3개 열로 보려면 [기준 실행](https://github.com/knadalkim-a11y/team-agent-poc/actions/runs/42962981781)의 browser evidence를 풀어 ‘이전 빌드 캡처 폴더’에서 고른다. 이전 화면과 동일한 상태의 캡처가 없으면 그 차이를 표시한다. 파일 선택은 브라우저 안에서만 처리한다. 데이터 건수·예시 문구가 다른 두 이미지를 전체 픽셀 점수로 판정하지 않는다.

## 기존 제품 흐름을 채택한 두 화면의 피그마 보정안

- **B1** `835:323`의 가운데 프레임 `835:456`에 실제 제목·이름 검색·선택 범위의 절차 목록·각 행의 유형/단계 수/게시 표시를 배치한다. 새 워크플로우는 현재 목록의 아래에서 이름·목적을 받는다. 예시를 고른 뒤 질문 1~5를 거치는 화면은 별도 작성 방식의 검토안으로 분리한다. [기존 목록 결정](../docs/mockups/ees-work/TASK.md#operations31-authoring12-parity-20261030)
- **A8** `960:1177`는 왼쪽 작업 위치를 공유한다. 중앙에는 선택한 절차의 단계 개요를 배치한다. 공장이 필요하면 현재 위치를 안내하고, 명시적 시작 또는 기존 진행 건 열기로 이어진다. 조회·취소·화면 이동은 새 회차를 만들지 않는다. [기존 시작 계약](../docs/mockups/ees-work/TASK.md#operations-entry-legacy-removal-20261030)

## 판정의 근거

같은 통합 커밋의 실제 브라우저 PNG·치수·권한·저장·실행 테스트 결과를 함께 읽는다. 디자인 참고 이미지 8장은 실제 제품의 합격 캡처 수에 포함되지 않는다. 실행 당시 응답·권한과 사내 운영 데이터는 별도 환경이며, 사내 배포·사용자 확인은 이 PR의 범위에 포함되지 않는다.

## 첫 통합 실행의 회귀 확인

[0cc2ee2의 통합 실행](https://github.com/knadalkim-a11y/team-agent-poc/actions/runs/42978670712)에서 제품 빌드·패키징·실제 전체 제품 시험은 성공했다. Linux·Windows 서비스 시험은 T01의 예전 안내 문구 및 전체 class 문자열을 요구하는 Node 단언 4곳에서 실패했다. Native C66은 모든 일반 배지를 금지하여 실제 연결 버전 표시에서 실패했다. 목록 검색·범위 보존, 사용 불가 상태·시험 전 사용 금지는 계속 검증하며, 도구 버전은 조회 권한이 있을 때만 표시하고 권한 회수 후에는 숨기는 조건을 검증한다. 이 실행에서는 A4-2 상태 추적, 회차 왕복, B2/B4와 B6~B8의 합성 자료 시나리오가 통과했다. 최종 결과는 PR의 마지막 커밋을 기준으로 확인한다.

## 2026-11-12 · 배포 검증에서 확인한 초안 복원과 탭 전환

- [첫 번째 실행](https://github.com/knadalkim-a11y/team-agent-poc/actions/runs/43109448017/job/130824059158)에서는 ‘게시 기록’ 탭의 배경색이 투명해지는 120ms 동안 중간색을 읽었다. 검사에서 포인터를 뺀 뒤 같은 탐색 영역에 있는 모든 탭의 배경이 투명해질 때까지 기다린다. 탭 색상·높이·밑줄의 기존 합격 기준을 유지한다.
- [두 번째 실행](https://github.com/knadalkim-a11y/team-agent-poc/actions/runs/43109448017/job/130830806860)에서는 기존 대화를 열고 ‘작성 중인 내용’을 입력한 뒤 서식 있는 프롬프트를 삽입했을 때 이전 초안이 나타났다. 저장된 본문 복원과 사용자가 선택한 프롬프트의 변수 확장 시점을 구분한다. 회귀 검사는 새로 입력한 문장, 단락 순서, 굵게 표시한 텍스트 및 전송 요청 0건을 확인한다.
- 로컬 Chrome 153과 위 커밋의 CI 배포용 wheel에서 사용자 정보 조회 응답을 보류하면 초안 복원이 완료를 반환한 뒤 물리 입력이 이전 초안으로 덮였다. 수정한 복원 경로는 작성 중인 글을 동기적으로 편집기에 반영하며, 변수 형태의 텍스트도 처음 입력한 대로 보존한다. 기존 저장 프롬프트 삽입은 변수 확장을 계속 수행한다. 같은 wheel에서 수정한 탭 검사 C18 전체가 5회 연속 통과했다.

## 2026-11-16 · 워크스페이스 네 메뉴 화면 검토 목업 1판

- **증상(사용자 보고):** 워크스페이스의 업무 절차·도구·작업 지침·참고 문서 화면이 제품이 아니라 PoC용 HTML처럼 보인다.
- **환경·기준:** main `a11e41755b4cf8c3face5e0d9b6e6d51888e1ad7`, Linux 개발 환경, Playwright Chromium(headless). 실제 제품은 띄우지 않았다.
- **확인한 증거:** [도구 v11 제품 비교](artifacts/api-tools-20261113/README.md)의 제품 캡처 6장 중 목록·편집·등록·작업 연결과, 이 기록의 Figma 기준 화면 중 업무 절차·작업 지침·참고 문서를 봤다. 도구 화면의 제품과 Figma 경계 차이는 0~1px로 기록돼 있다. 작업 지침·참고 문서의 실제 제품 화면(Native `/workspace/skills`, `/workspace/knowledge`)과 Figma 원본 파일은 열지 못했다.
- **원인 판단:** 구현 차이가 아니라 설계의 시각 위계와 배치다. 네 메뉴가 서로 다른 목록 표현을 쓰고, 넓은 영역에서 입력칸만 늘어난다. 작업 지침·참고 문서의 제품 화면에 대한 판단은 Figma 기준 화면에 근거한 것이다.
- **조치:** 제품은 바꾸지 않고 [검토 목업 1판](../docs/mockups/ees-work/design-mock-17-workspace.html)을 만들었다. [계약](../docs/mockups/ees-work/TASK.md#workspace-screens-20261116).
- **검증:** `node evals/artifacts/workspace-screens-20261116/check_mock.js`로 1920×1080, 1366×768, 480×800에서 [167/167](artifacts/workspace-screens-20261116/validation-report.json). 화면 전환, 메뉴와 머리띠의 일치, 가로 넘침 없음, 찾기와 빈 결과, 서비스 묶음 접기, 탭, 저장 전 표시, 좁은 창의 채팅 겹침과 Escape, 페이지·콘솔 오류와 네트워크 요청 0을 본다. 첫 실행부터 통과했다.
  - 검사 전에 캡처를 보고 고친 것: 선택 표시 동그라미가 20px로 커진 것, 안내 문장이 낱말 중간에서 줄바꿈된 것, 480 폭에서 왼쪽 메뉴가 접히지 않아 가운데가 좁아진 것.
  - 목업 빌더가 기존 15번 목업 원본을 다시 만들 수 있는지 먼저 확인했다. 결과 파일은 커밋된 15번과 달랐는데, 차이는 그 뒤 바뀐 제품 CSS가 들어간 것이다. 15번 파일은 고치지 않았다.
  - `tests/test_build_design_mock.py`의 커밋된 목업 글꼴 형식 검사가 새 파일을 함께 본다.
