변경 전까지 3개 열로 보려면 [기준 실행](https://github.com/knadalkim-a11y/team-agent-poc/actions/runs/42962981781)의 browser evidence를 풀어 ‘이전 빌드 캡처 폴더’에서 고른다. 이전 화면과 동일한 상태의 캡처가 없으면 그 차이를 표시한다. 파일 선택은 브라우저 안에서만 처리한다. 데이터 건수·예시 문구가 다른 두 이미지를 전체 픽셀 점수로 판정하지 않는다.

## 기존 제품 흐름을 채택한 두 화면의 피그마 보정안

- **B1** `835:323`의 가운데 프레임 `835:456`에 실제 제목·이름 검색·선택 범위의 절차 목록·각 행의 유형/단계 수/게시 표시를 배치한다. 새 워크플로우는 현재 목록의 아래에서 이름·목적을 받는다. 예시를 고른 뒤 질문 1~5를 거치는 화면은 별도 작성 방식의 검토안으로 분리한다. [기존 목록 결정](../docs/mockups/ees-work/TASK.md#operations31-authoring12-parity-20261030)
- **A8** `960:1177`는 왼쪽 작업 위치를 공유한다. 중앙에는 선택한 절차의 단계 개요를 배치한다. 공장이 필요하면 현재 위치를 안내하고, 명시적 시작 또는 기존 진행 건 열기로 이어진다. 조회·취소·화면 이동은 새 회차를 만들지 않는다. [기존 시작 계약](../docs/mockups/ees-work/TASK.md#operations-entry-legacy-removal-20261030)

## 판정의 근거

같은 통합 커밋의 실제 브라우저 PNG·치수·권한·저장·실행 테스트 결과를 함께 읽는다. 디자인 참고 이미지 8장은 실제 제품의 합격 캡처 수에 포함되지 않는다. 실행 당시 응답·권한과 사내 운영 데이터는 별도 환경이며, 사내 배포·사용자 확인은 이 PR의 범위에 포함되지 않는다.

## 첫 통합 실행의 회귀 확인

[0cc2ee2의 통합 실행](https://github.com/knadalkim-a11y/team-agent-poc/actions/runs/42978670712)에서 제품 빌드·패키징·실제 전체 제품 시험은 성공했다. Linux·Windows 서비스 시험은 T01의 예전 안내 문구 및 전체 class 문자열을 요구하는 Node 단언 4곳에서 실패했다. ### 2026-11-16 · 1판 재검토와 2판

- **요청:** 사용자가 1판이 넓은 화면을 잘 쓰는지, 의미 없는 설명 문구와 라벨이 없는지 다시 검토하라고 했다. 위 1판 기록은 당시 내용이다. 1판은 커밋 `b24fedf`에 있다.
- **재는 방법:** 1920×1080에서 가운데 업무 영역 안의 글자 줄과 입력칸·표시가 차지하는 넓이를 8px 격자로 세어 영역 넓이로 나눴다. 채워진 정도를 비교하는 거친 값이며 좋은 배치의 기준은 아니다. 1판은 별도 측정 스크립트로, 2판은 검사 스크립트의 같은 계산으로 쟀다.

| 채팅 열림 | WS4 API 상세 | 11%, 높이의 96% 사용 | 9%, 두 열로 나눠 한 화면 안에 들어옴 |

  1. **다른 회차에서 실행됨:** 이미 열린 회차가 있어 새 회차를 시작하지 못하는 절차에서, 시작 전 화면의 줄 ‘실행’을 누르면 열린 회차로 옮겨 간 뒤 그 회차에서 작업을 실행했다. 시작 함수가 ‘새 회차를 만들었다’와 ‘다른 회차로 갔다’를 구분하지 않고 돌려주었다. 이제 새로 만든 회차의 id만 돌려주고, 줄의 ‘실행’은 그 회차에서만 실행한다.
  2. **읽지 못한 값은 조용히 무시됨:** JSON으로 적는 값이 틀린 형식이면 그 작업의 값 전체를 읽지 못했는데 그대로 이전 값으로 실행했다. JSON 값은 줄 아래에서 묻지 않고(지금처럼 시작 창), 값을 읽지 못하면 아무것도 보내지 않고 알린다. 여러 줄로 적는 값도 입력 중에는 다시 그릴 때 건드리지 않는다.
  3. **값을 넣을 수 있지만 저장되지 않는 줄:** 확인 항목 작업은 체크할 때 값을 저장하지 않아, 필수 값이 있으면 서버가 체크를 계속 거절했다. 변경 요청 작업은 줄에 값을 저장할 동작이 없었다. 체크할 때 값을 먼저 저장하게 했고, 줄에 저장할 동작이 없는 작업은 줄 아래에서 묻지 않는다.
  4. **답한 작업의 값을 고치고 같은 판정:** 값은 저장되어 ‘다시 검토 필요’가 되는데 같은 판정은 ‘할 일 없음’으로 걸러져 다시 확인되지 않았다. 다시 검토가 필요한 작업은 같은 판정도 다시 보낸다. 서버가 받아 완료로 돌리는 것을 실제 브라우저 시험에 넣었다.
  5. **누르지 않은 작업의 값이 함께 저장됨:** 어느 작업을 누르든 넣어 둔 값 전부를 저장해, 그사이 다른 곳에서 새로 저장된 값을 덮을 수 있었다. 누른 작업의 값만 저장한다.

  8. **서버 거절이 다른 작업을 엶:** 같은 값을 두 작업이 묻는 절차에서 거절 문구가 마지막 작업 아래에 표시됐다. 누른 작업에 표시한다.

- **두 번째 독립 검토(2026-11-19, 수정 커밋 `29ebd65`, PR #153을 연 뒤):** 수정도 실행 경로를 건드렸는데 독립 검토 없이 들어가 같은 방식으로 다시 맡겼다. PR의 자동 리뷰(Codex)는 지적 없이 ‘완료하지 못함’으로 끝났다. 처음 맡긴 검토는 사용량 한도로 중간에 멈춰 다시 맡겼다.
  1. **저장할 동작이 없는 줄의 칸이 열려 있음(확인):** 모두 체크한 확인 항목 작업, 답할 권한이 없는 사람 작업, 지금 실행할 수 없는 도구 작업에서도 칸을 고칠 수 있었다. 거기 넣은 값은 나중에 ‘지금 실행’이 함께 저장했고, 그러면 완료된 확인 항목이 다시 검토로 돌아가 체크가 모두 풀렸다. 앞선 수정 3의 규칙을 작업의 종류로만 정하고 지금 상태를 보지 않은 것이 원인이다. 칸은 그 줄에 저장할 동작이 있을 때만 열고, ‘지금 실행’은 그 단계의 도구·AI 작업 값만 저장한다.
  2. **다른 사람의 답과 같은 판정이 무시됨(코드 추적으로 확인):** 다른 사람이 ‘미흡’으로 답한 작업의 값을 고치고 ‘미흡’을 다시 누르면 값만 저장되고 답은 보내지 않았다. 값 저장은 완료·확인 대기 상태만 다시 검토로 돌리고, 결과가 지났다는 표시는 지금 보는 사람의 시도에만 붙기 때문이다. 이번에 값을 저장한 답은 같은 판정이라도 보낸다. 서버는 사람 작업의 답마다 새 시도를 만들어 받는다(코드로 확인).
  3. **절차 바로 아래 작업의 값을 어디서도 묻지 않음(구현 커밋부터 있던 빈틈, 확인):** 단계에 속하지 않은 작업은 줄이 없는데 그 값을 시작 창에서도 뺐다. 단계 안의 작업만 줄에서 묻는다.
  - 고치지 않고 정한 것: 진행 건 화면의 ‘단계 실행’·‘절차 실행’은 단계 화면에 넣어 두고 저장하지 않은 값을 보내지 않는다. 그 화면에 보이지 않는 값이고 단추 옆 문구도 ‘저장한 입력으로 실행’이다.
  - 검토가 문제없다고 본 것: 시작 함수를 부르는 다른 곳, 한 번 눌러 두 번 답하는 경우, 체크를 거절했을 때 체크 칸이 돌아오는 것, 저장 중에 다시 넣은 값, 공장이 들어간 저장 범위의 넘김, 바뀐 함수 모양을 옛 방식으로 부르는 곳.
  - 새 Node 시험 네 개가 고치기 전 코드에서 실패하는 것을 확인했다.
- **PR #153 자동 리뷰(Codex, 2026-11-19, `e642da3`):** 처음 실행은 ‘완료하지 못함’으로 끝났고, 새 커밋에서 다시 돌아 두 건(P2)을 찾았다. 둘 다 코드로 확인했다.
  1. **바꾼 값을 저장하지 않고 이전 결과를 확정함:** 실행한 도구 작업의 값을 줄 아래에서 바꾸고 ‘목록 확정’을 누르면, 확정은 작업 화면의 입력만 확인하고 줄 아래의 값은 보지 않았다. 서버는 저장된 값과 실행 때 값이 다를 때만 거절하므로, 저장하지 않은 값은 막지 못한다. 그래서 화면에 보이는 값과 다른 결과가 확정됐다. 도구 작업의 판정도 같았다(이쪽은 값을 저장한 뒤 판정을 보내 서버가 거절하고, 화면 위에 오류가 떴다). 바꾼 값이 있으면 값만 저장하고 확정·판정은 하지 않는다. 작업은 다시 검토로 돌아가고 그 줄의 ‘실행’에 초점이 간다.
  2. **다른 사람이 바꾼 값을 덮어씀:** 줄 아래에 값을 넣는 동안 다른 사람이 같은 값을 저장하면, 실행할 때 그 값을 알리지 않고 덮어썼다. 작업 화면의 입력은 처음 값과 회차 버전을 기억해 두었다가 멈추게 되어 있는데, 줄 아래 값에는 그 장치가 없었다. 넣기 시작할 때의 저장값을 기억하고, 그 값이 바뀌었으면 저장하기 전에 멈추고 칸에 ‘다른 사람이 바꾼 값 · …’을 보인다. 한 번 더 누르면 넣은 값을 저장한다.
  - 두 독립 검토가 놓친 이유: 두 검토 모두 실행·판정의 흐름과 값을 저장하는 범위를 보았고, 다른 사람이 동시에 쓰는 경우와 작업 화면에 이미 있던 보호(입력 비교)를 줄 아래 값과 견주지 않았다.
  - 새 Node 시험 두 개가 고치기 전 코드에서 실패하는 것을 확인했다.

## 2026-11-20 · 시스템 공용 계정 하나를 여럿이 함께 쓰며 업무 절차 만들기(진단)

- **요청·범위:** 사용자가 ‘할 일’ 화면 질문에 이어 “지금 당장 필요한 기능은 시스템별 공용 계정을 사람들이 같이쓰면서, 시스템별 워크플로우를 만드는게 가장 급하거든? 이거에 방해가 된다고 느껴서 그런거같아”라고 했다. 개발 AI가 다음 두 가지를 제안했고 사용자가 “응 그렇게 진행해줘”라고 했다.
  - 목업 20번 구현은 작업 브랜치에 두고 main 반영·사내 적용을 보류한다.
  - 같은 공용 계정으로 두 사람이 동시에 각자 업무 절차를 만들고, 게시하고, 시험 실행하는 흐름을 실제 제품에서 처음부터 끝까지 따라가 막히는 곳을 찾는다.

  진단만 했고 제품 코드는 바꾸지 않았다.
- **환경:**
  - 개발 컨테이너에서 실제 Open WebUI 앱(`0.11.3+ees.14`)을 임시 DB로 띄웠다. 모델은 합성이다. Confluence 연결은 설정하지 않아 가이드의 찾기는 모두 연결 오류로 끝난다.
  - 두 판으로 했다.
    - 사내에서 쓰는 main `e494605`: 그 커밋의 worktree로 빌드했다(wheel SHA256 `048945bd…`).
    - 작업 브랜치 `a8f9ee1`(목업 20번 구현): wheel SHA256 `afb59a57…`.
    - 두 빌드 모두 빌드 입력 143개가 각 커밋의 파일과 같다.
  - 관리자가 아닌 계정 ‘EMS 공용 계정’에 관리자 전용 명령(`save_access`)으로 EMS 담당·참여 권한을 줬다. 같은 계정으로 두 번 로그인해 세션 두 개를 만들었다. 브라우저 두 개(사람 A·B, Chromium 153, 1920×1080)가 실제 단추를 누르고 글자를 넣었다.

- **방법:**
  - 하루 일의 순서로 시나리오 16개를 두 판에서 돌렸다. 각자 만들기, 같은 절차 함께 고치기, 저장하지 않은 채 새로고침, 화면 위치, 시험 실행 겹침, 동시에 시작, 게시 내림, 같은 이름, 시작 값, 30초 갱신, 고쳐서 다시 게시, 오류가 뜬 채 시작, 다른 사람 회차가 열린 뒤 ‘실행’·‘찾기’, 이름·목적 칸, 저장 직후 시작, 열어 둔 창이다.
  - 코드 읽기를 다섯 갈래(작성, 실행, 화면 상태, 권한, 기존 기록)로 나눠 맡겼다. 이 기록에는 끝난 작성·실행 두 갈래의 결과를 썼다. 나머지 세 갈래는 반박 검토와 빠진 상황 점검이 같은 곳을 다뤄서 끝나기 전에 멈췄다. 화면에서 보지 않은 의심 네 가지는 시나리오를 더해 실제 화면에서 확인했다.
  - 찾은 것마다 다른 AI가 반박을 시도했다. 본 것은 시험 틀 탓인지, 코드상 원인, ②에 주는 영향, 2026-11-03 결정에서 받아들인 것인지, 일하는 방식으로 피할 수 있는지다. 반박하는 AI는 화면을 띄우지 않고 기록·캡처·코드만 읽었다.
  - 처음 몇 번은 일회용 스크립트의 문제(선택자, 열린 창을 닫지 않음, 기록 이름 중복)로 시나리오 일부가 멈췄다. 고쳐서 다시 돌렸고, 결과에는 끝까지 돈 실행만 썼다. 제품 오류(페이지 예외)는 모든 실행에서 0건이었다.
- **결론:**
  - 각자 **다른** 절차를 만들고, 게시하고, 시험하는 것은 서버에서 서로 막지 않는다. 만들기·저장·게시·시작이 절차마다 따로이고, 한 절차의 회차가 열려 있어도 다른 절차의 회차가 시작됐다.
    - 다만 두 사람이 각자 자기 절차의 회차를 나란히 돌린 시나리오는 없다. 위 확인과 코드로 판단했다.
    - 계정 하나에 저장되는 화면 상태(아래 8·9번)는 서로 다른 절차를 하는 사람끼리도 영향을 준다.
  - 서버는 늦게 온 저장·판정을 거절한다. 다른 사람 것을 말없이 덮어쓰지 않는다.
  - 걸리는 곳은 세 상황에서 나온다.
    - 같은 절차를 둘이 **시험**할 때
    - 같은 절차를 둘이 **고칠** 때
    - 계정 하나에 하나만 저장되는 **화면 상태**
  - 거절당한 사람이 혼자 빠져나오기 어렵고, 입력이 말없이 사라지는 곳이 있다.
  - 두 판의 결과는 같다. 처음 누를 때 나오는 문구 하나가 달랐는데, 판 차이가 아니라 갱신 시점 차이다.

- **코드로만 확인한 것(화면에서 보지 않음):**
  - 게시된 절차는 ‘저장’할 때마다 새 판으로 바로 게시된다. 그래서 다른 사람 절차를 고치면 모두의 다음 회차에 바로 쓰인다. 이것은 화면에서도 봤다. 게시된 절차에서 ‘저장’(단추 이름은 ‘저장 · 게시’가 아니라 ‘저장’)을 두 번 누르자 게시 판이 1에서 3이 됐다.
  - 게시 상태를 바꾸면 확인 없이 바로 저장된다.
  - 절차는 지울 수 없다. 게시하지 않은 절차를 다른 사람이 덮어쓰면 제품 안에서 되돌릴 수 없다(초안은 판이 남지 않는다).
  - 누가 언제 바꿨는지 보여 주는 곳이 없다. ‘게시 기록’은 게시한 사람으로 계정 ID 문자열을 보여 준다.
  - 시험하려면 게시해야 한다. 게시하면 그 시스템에 접근할 수 있는 모든 계정의 업무 목록에 보인다. 실행 기록에도 시험이라는 표시가 없다.
  - ‘업무 설정 값 편집’이 충돌하면 창의 값이 사라진다. 그런데 문구는 ‘작성 중인 변경을 유지했습니다’라고 한다.
  - 같은 저장본에서 ‘내용 확인’을 다시 누르면 처음 결과를 다시 보여 준다. 다른 사람이 설정이나 도구를 고쳐도 새로고침 전까지 같다.
  - 회차 안에서 충돌하면 화면 위 빨간 줄로 나오고, 다시 조회하는 단추가 없다.
  - **EES 변경 요청의 승인:** 작업의 ‘요청 승인’을 ‘서로 다른 담당자 1명’이나 ‘2명’으로 두면 공용 계정은 자기 요청을 승인할 수 없다(`self_approval_forbidden`, 두 판 같음). 요청이 승인 대기에 멈추고, 승인 역할이 있는 다른 계정이 있어야 풀린다. 기본값 ‘필요 없음 · 최종 확인 필요’에서는 생기지 않는다. 2026-11-03 결정에서 다루지 않았다. 반박 검토 뒤에도 ‘막는다’로 남을 수 있는 것은 이것 하나다.
  - 대화: Open WebUI는 대화가 끝났다는 알림을 같은 계정의 모든 창에 보낸다. 다른 사람 대화의 제목과 내용 일부가 15초 동안 뜨고, 누르면 그 대화로 간다(Open WebUI 원본 코드). 2026-11-03에 받아들인 것은 대화를 서로 볼 수 있다는 것까지였다.
  - 업무 설정 값을 저장하면, 그 절차의 열린 회차(다른 사람 것 포함)에서 끝난 작업이 ‘업무 설정 변경 후 재확인 필요’로 바뀐다.
  - 시험 회차가 실행 기록에 실제 회차와 섞여 쌓인다. 열린 회차에는 기한이 없어서, 끝내지 않은 시험 회차는 그 절차의 다음 실제 회차를 막거나 끌어들인다.

  - 실제 팀원의 사용
  - 시험 틀의 동시 누르기는 몇 ms 차이라 실제보다 빠르다.
