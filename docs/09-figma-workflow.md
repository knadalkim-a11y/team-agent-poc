# EES Work — Figma 중심 UI/UX 작업 가이드

이 문서는 화면을 설계·검토할 사용자와 구현을 맡는 AI의 지속 관리 원본이다. 매 대화마다 새 목업 지시서·인계서를 만들지 않는다. 현재 진행·접근 제한은 [STATUS](STATUS.md), 날짜별 검토·검증 증거는 [기존 평가 기록](../evals/ees-work-runtime-poc.md#figma-preparation-20260917)에서 확인한다. 도입 준비 문서와 Figma 실제 반영·제품 구현·사내 배포를 구분한다.

<a id="ownership"></a>

## 1. 관리 원본과 적용 범위

**Figma는 승인된 시각 설계·상호작용의 기준이며, 전체 제품의 유일한 원본은 아니다.**

| 관리 대상 | 원본 | 다른 곳에 남길 내용 |
|---|---|---|
| 화면 배치·서체·색상·컴포넌트·클릭 흐름 | 승인된 Figma 화면 revision | Git에 해당 화면/노드·revision·승인 범위 링크 |
| P/T/J 의미·완료 판정·권한·공통 정책 | [Contract·Runtime 설계](08-ees-work-contract-runtime.md)와 해당 코드 | Figma에 사용자에게 보이는 상태와 짧은 제약 표시 |
| 실행 Action·실제 저장·테스트·배포 | Git 코드와 기존 평가 기록 | Figma에 구현 여부를 추정해 표시하지 않음 |
| 실제 진행 건·사용자 자산·자격증명 | 승인된 사내 시스템 | Figma/Git에는 합성 예시·비밀값 없는 요약만 |

새 UI나 의미 있는 상호작용 변경은 요구사항 → Figma → 사용자 클릭 검토 → 특정 revision 승인 → 코드 구현 → 시각/기능 검증으로 진행한다. 작은 문구 수정·화면과 무관한 변경·긴급 장애 수정에 별도 대형 디자인 단계를 강제하지 않는다. 긴급 수정으로 화면이 달라지면 변경 범위의 Figma와 인계 기록을 후속 정합화한다.

기존 HTML 목업은 과거 참고로 보존한다. 새 승인 이후 같은 화면의 Figma와 HTML을 각각 원본처럼 계속 갱신하지 않는다. 기존 WebUI 컴포넌트·테마를 활용하고 Figma 도입만으로 UI 프레임워크·빌드·서버·배포 구조를 교체하지 않는다.

## 2. 파일 구성: 하나의 파일에서 작게 시작

대상은 기존 [EES Work — Workspace UX Mockup](https://www.figma.com/design/XK2wTos6sEuxSHhIj7cqg6)이다. 기존 파일을 복제하거나 다른 팀으로 옮기지 않고 접근 가능한 시점에 현재 구조·사용자 수정을 먼저 확인한다.

다음은 **적용할 구조**이며 생성 완료 목록이 아니다. 처음부터 많은 페이지·빈 폴더·컴포넌트를 만들지 않는다. 파일/플랜 제약이 있으면 같은 페이지의 영역으로 구성하되 기존 프로토타입 연결을 보존한다.

| 영역 | 내용 |
|---|---|
| `00 Guide` | 검토 시작 링크, 합성 시연 표시, 이번 검토 범위, 승인된 revision 링크, Git 가이드 링크 |
| `10 Foundations` | 실제 쓰는 색상/간격/서체 변수, 최소 공통 컴포넌트와 사용 예 |
| `20 Workspace` | 공통 셸, P/T/J, 패널 닫힘, 오류·확인·이력 상태, 해당 업무의 Prototype 흐름 |

P/T/J와 그 전환 대상은 같은 페이지에 둔다. 화면 상태별로 페이지를 늘리지 않는다. Workspace 절차 편집은 대표 업무 검토 뒤 같은 페이지의 별도 영역에서 시작한다. 사용하지 않는 다크 테마·모바일·전사 라이브러리·분석/전문가 전체 화면은 준비 단계의 필수 조건으로 넣지 않는다.

### 공통 화면 기준

기준 해상도는 1920×1080이다. 업무 탐색 사이드바, 가운데 대화, 오른쪽 업무 패널의 관계와 밝은 회색/화이트 톤·한글 가독성을 유지한다. 오른쪽 패널을 임의로 하단으로 바꾸지 않는다. 패널 폭·리사이즈·텍스트 줄바꿈은 실제 렌더링으로 확인하며 최초 치수를 영구 규격으로 고정하지 않는다. 구현 인계 때 더 좁은 데스크톱도 확인한다.

제품의 기존 서체·색상과 이미 생성된 Figma 변수를 먼저 재사용한다. 서체 이름과 실제 사용 가능한 스타일을 조회하고, 누락 시 폴백을 명시한다. 라이선스 확인 없이 폰트 파일을 배포하지 않는다. 이모지를 쓰지 않고, 읽기 어려운 장문·작은 글자·색상만으로 구분하는 상태를 피한다. 모델명은 교체 가능한 표시값이며 화면/도구 코드에 특정 모델을 고정하지 않는다.

### 최소 공통 컴포넌트

처음에는 `Button`, `Field`, `StatusBadge`, `WorkTreeRow`, `PanelHeader`, `CriterionRow` 여섯 종류만 실제 사용처를 보며 정리한다. 기존 사용 컴포넌트와 해당 코드 위치를 먼저 확인하고, 필요한 경우에만 새 로컬 컴포넌트를 만든다. 초기에는 실제 쓰는 기본/선택/비활성/오류 상태만 만들며 모든 조합의 variant를 생성하지 않는다.

관련 컨테이너는 Auto Layout으로 묶고 반복 요소는 instance로 사용한다. 색상·간격·모서리 값은 기존 token에 연결한다. 토큰을 생성했다는 사실만으로 화면 전체에 적용된 것으로 기록하지 않는다. Figma의 프레임을 코드 컴포넌트 하나씩으로 기계적으로 대응시키지도 않는다.

## 3. P/T/J 화면 계약

[업무 규격](08-ees-work-contract-runtime.md#vision)을 UI에서도 유지한다. 사람에게 보이는 업무 계층은 P/T/J이고 Step·Action·Check는 새 탐색 계층이 아니다.

| 화면 | 먼저 보여줄 정보 | 기본 행동 |
|---|---|---|
| P | 전체 목표·완료 기준, 직계 T 진행과 남은 일 | T로 내려가기, 실행 가능한 범위 확인 |
| T | 단계 목적·완료 기준, 선행 조건, 하위 J 상태·다음 행동 | J로 내려가기, 미완료 사유 확인 |
| J | 목표, 최근 결과, 기준별 판정·근거, 입력과 다음 행동 | 입력 보완, 수행/재시도, 실제 사람 확인 |
| Workspace | 업무 정의 초안, 구조 검증 결과, 게시 범위 | 작성·검토·구조 검증·게시를 구분 |
| 대화 | 현재 선택 업무, 질문·가이드, 부족한 입력, 제안과 결과 | 패널과 같은 업무를 자연어로 조작 |

일상 담당자에게 도구·스킬·검증기 선택을 요구하지 않는다. 실행 설정은 상세/Workspace에 두되 미연결·권한 부족은 기본 화면에서도 알려준다. 업무 선택 자체에 불필요한 시작 절차를 추가하지 않는 방향을 유지하며, 최초 입력/실행의 진행 건 생성 시점은 현 코드 계약을 대조한 뒤 확정한다. 과거 실행을 덮지 않고 재수행은 새 실행으로 구분한다.

실행 성공과 기준 충족을 구분한다. FAIL, UNKNOWN, 선행 대기, 적용 제외, 미수행, 입력 변경으로 무효화된 결과를 하나의 실패/성공으로 합치지 않는다. 하위 절차 완료를 P의 최종 목표가 증명된 것처럼 표현하지 않는다. 사람이 확인할 기준은 AI 초안과 실제 확인 기록을 구분한다.

## 4. Prototype은 한 업무의 왕복 경로부터

첫 검토 묶음은 `P → T → J → 결과/근거 → 상위 화면`과 `패널 닫기 → 같은 업무에서 다시 열기`다. 이후 그 업무에 필요한 입력 부족 → 실행 중 → 성공/실패/UNKNOWN → 재시도 → 사람 확인 → 완료 이력을 추가한다. 모든 화면을 그린 뒤에야 첫 구현을 시작하는 방식은 쓰지 않는다.

프로토타입 안에 “합성 시연 · 실제 도구/DB 실행 없음”을 표시한다. 실행 버튼은 준비된 예시 결과로 전환할 뿐이다. 자유 입력·실제 AI 응답·권한 검사·영속 저장을 구현했다고 설명하지 않는다. 자연어 위임은 미리 정한 예시 문구의 시연과 실제 제품의 모델 호출을 구분한다.

검토 대상의 버튼에는 정상적인 다음 상태·복귀 경로가 있어야 한다. 아직 시연하지 않는 기능은 비활성/범위 밖이라고 명확히 표시한다. 닫기/뒤로 가기는 업무 선택·입력 초안을 잃지 않아야 하고, 현재 선택한 트리·대화 범위·브레드크럼·업무 패널이 일치해야 한다. 화면에 성공을 표시하면서 기준 체크는 미확인으로 남기는 등의 모순을 확인한다.

프로토타입 클릭 검토는 Figma의 Present 흐름에서 수행한다. 연결이 저장된 것, 렌더링이 정상인 것, 사람이 실제로 눌러 확인한 것을 각각 기록한다. Figma 시연 통과를 제품 E2E 통과로 옮기지 않는다.

## 5. 승인과 코드 인계

화면은 `WIP → REVIEW → APPROVED`로 관리하되 프로젝트에서 정한 이름/표시 규칙이다. Figma 유료 Dev Mode의 상태 기능이 설치된 것처럼 설명하지 않는다. “깔끔하다”는 시각 방향 수락이며 모든 상태·권한·실행 흐름의 일괄 승인은 아니다.

승인 시 아래 항목을 해당 업무의 Git 작업/평가 기록에 한 번 남긴다. Figma에는 그 기록과 승인 대상 링크만 둔다. 진행 상태는 STATUS에서 관리하고 별도 DB·동기화 서비스·중복 승인표를 만들지 않는다.

```text
업무/화면 ID와 검토 시나리오:
Figma file key + node ID + revision/버전 링크:
고정 스냅샷 참조 + 승인자/날짜 + 승인 범위:
관련 Contract/코드 기준 커밋:
UI 행동 → 기존 공통 Action/도구 → 권한·입력·상태 변화:
합성 시연 / 구현됨 / 미연결 구분:
기대 결과·예외·사용성/E2E 확인 조건:
```

수정 가능한 노드 URL 하나만으로 승인본을 고정하지 않는다. Figma 버전 참조 또는 식별 가능한 스냅샷과 그 해시를 함께 남기고, 승인 뒤 바뀐 화면은 새 revision으로 검토한다. 현재 승인 원본의 실제 존재·사용자 수정 여부를 재조회하지 못하면 임의로 “최신 승인본”을 재작성하지 않는다.

모든 상호작용 요소는 구현 인계 전에 대응을 분류한다. P/T/J 선택, 입력 수정, 실행/재시도, 확인, 이력, 근거 조회, 필터, 패널 열고 닫기 모두 포함한다. 업무 상태를 바꾸는 UI/AI는 같은 서버 Action·권한·revision·결과를 사용한다. 패널 표시 같은 UI 상태도 에이전트가 제어할 수 있는 명시적 UI action으로 연결하되 이를 위해 불필요한 업무 DB 쓰기를 추가하지 않는다. 현재 없는 API 이름을 목업에서 만들어 구현된 계약처럼 전달하지 않는다.

| 행동 예 | Figma 검토 | 제품에서 따로 확인 |
|---|---|---|
| P/T/J 선택 | 선택 표시와 패널 내용 일치 | UI/AI의 동일 대상 선택·권한·기록 |
| 입력 보완·재시도 | 이전 시도와 새 결과의 차이 | revision/근거 무효화·중복 요청·늦은 결과 |
| 사람 확인 | 초안·확인 전·확인 후 구분 | 실제 사용자 행위와 권한, AI 대리 승인 금지 |
| 패널 닫기·다시 열기 | 같은 맥락으로 복귀 | 상태 보존, 키보드 포커스·리사이즈 |
| 이력·근거 조회 | 읽기 전용과 복귀 위치 | 조회가 현재 실행·선택을 변경하지 않음 |

코드 생성 결과는 참고로 받아 기존 WebUI 구성·자산·저장 계약에 맞게 구현한다. Figma 레이어를 통째로 새 프론트엔드로 치환하지 않는다. 형식상 Code Connect는 초기 필수가 아니다. 우선 인계 기록에 실제 코드 경로를 연결하고 반복 사용이 확인된 뒤 지원 조건을 검토한다.

시각 검증은 같은 데이터·상태·해상도에서 Figma와 제품의 배치·폭·줄바꿈·상태 표시를 비교한다. 기능 검증은 기존 테스트 체계에서 UI 행동과 AI의 동일 요청이 같은 결과를 내는지 확인한다. 대비·포커스·키보드·좁은 창·빈 결과·권한 부족도 변경 범위에 포함한다. 미실행 플랫폼은 그대로 남긴다.

## 6. 접근·보안·도구 사용

2026-09-17 공식 안내 확인 기준, Starter MCP 읽기 한도는 월 최대 20회이며 Professional의 Dev/Full은 일 최대 200회·분당 10회다. 이는 일반 Figma 화면을 사람이 클릭할 수 있는 횟수와 다르다. 일부 쓰기 도구의 예외가 모든 `use_figma` 호출을 무제한으로 보장하지 않는다. 한도 오류가 나오면 반복 호출·다른 계정/접속 경로 우회를 하지 않는다. 공식 수치와 실제 오류를 각각 기록하며 초기화 시점을 추정하지 않는다. [Figma MCP 접근 안내](https://developers.figma.com/docs/figma-mcp-server/rate-limits-access/).

지속적인 AI 설계·검토와 직접 편집까지 하려면 Professional + Full 좌석을 검토한다. Dev 좌석은 Figma Design의 보기/댓글과 개발용 기능 중심이므로 Full과 같지 않다. 좌석과 파일별 편집 권한은 별개다. 다른 팀만 업그레이드한 뒤 해당 파일 권한/플랜도 바뀌었다고 가정하지 않는다. 결제·좌석 변경·파일 이동·공개 공유는 사용자가 별도로 결정하며 이 가이드 작성으로 실행하지 않는다. [좌석 안내](https://help.figma.com/hc/en-us/articles/360039960434-Manage-seats-in-Figma).

Code Connect는 공식 안내상 Organization/Enterprise와 Dev/Full 조건이 있으므로 이를 쓰기 위한 상위 요금제 구매를 준비의 선행조건으로 두지 않는다. [Code Connect 조건](https://developers.figma.com/docs/code-connect/). Prototype 흐름 자체는 모든 플랜에서 지원되며 편집 권한이 필요하다. [Prototype 흐름](https://help.figma.com/hc/en-us/articles/360039823894-Create-and-manage-prototype-flows).

Figma는 외부 설계 공간으로 취급한다. 실제 설비 식별자·공장 응답·사내 주소·PAT·사용자 대화·DB·미승인 소스/스크린샷은 올리지 않는다. 승인된 합성 자료만 사용하고, 공유 범위를 임의로 공개하지 않는다. 서비스 실행과 사내 배포에 Figma 연결을 필수 런타임 의존성으로 추가하지 않는다.

AI 작업은 한 업무 묶음의 현 상태 조회 → 작게 수정 → 관련 화면 렌더링/연결 검증으로 진행한다. 읽기 횟수를 줄이되 검증을 생략하거나 실패한 대형 쓰기를 무조건 재시도하지 않는다. 변경한 node ID를 기록하고 오류 뒤에는 실제 부분 변경 여부를 확인한다. 한도 차단 동안에는 계획·문서·확정된 자료 검토만 진행한다.

## 7. 첫 적용 순서와 완료 조건

| 단계 | 작업 | 완료 증거 |
|---|---|---|
| A. 접근 확인 | 계정/파일 권한·플랜 확인, 대상 파일의 현재 구조 한 번 조회 | 조회 결과 또는 차단 사유. 한도 차단을 승인 부족/파일 삭제로 단정하지 않음 |
| B. 파일 준비 | 기존 화면/ID 보존, Guide·Foundations·Workspace 구성, 실제 공통 요소만 정리 | 생성/수정 ID와 렌더링, 기존 흐름 보존 확인 |
| C. 첫 왕복 흐름 | P/T/J 정보 차이, 패널 닫기/재열기, 결과·근거·복귀 정리 | 연결 검사 + 사용자가 Present에서 클릭한 결과 |
| D. 한 업무 인계 | 실패/UNKNOWN/사람 확인을 포함한 필요한 상태와 UI/AI 행동 대응 | 정확한 revision과 승인 범위, 미구현 기능 표시 |
| E. 제한된 구현 | 승인된 묶음만 기존 코드에서 구현·비교 검증 | 코드 diff·관련 테스트·시각 대조·사용 안내 |

B~D가 끝나지 않았는데 “Figma 운영 준비 완료”라고 기록하지 않는다. E는 별도 구현 요청/범위 안에서 진행하며 준비 작업이 main 병합·배포 승인인 것은 아니다. 대표 실제 P/첫 읽기 J 선정은 기존 [Runtime 계획](08-ees-work-contract-runtime.md#pilot-selection)으로 유지한다. 공동 업무·전사 확장 목표를 없애지 않되 파일 구조 정리의 선행조건으로 늘리지 않는다.
