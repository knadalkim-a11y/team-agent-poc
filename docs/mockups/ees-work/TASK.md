# EES Work 목업 통합 작업 지시

역할: EES Portal 시연용 목업 통합·배포 담당자
저장소: knadalkim-a11y/team-agent-poc
입력: 이 문서와 같은 폴더의 [목업 원본](ees-demo-workspace.html). ZIP 첨부 없이 저장소 경로로 읽는다.

사내 EES Portal 안에서 합의한 EES Work 목업을 직접 조작하며 시연할 수 있도록 구현하라. 현재 이 경로에는 대화에서 만든 목업 원본과 후속 작업 지시를 보관한다. 실제 EES Portal 메뉴·화면·배포 연결은 아직 구현하지 않았다. 이번 작업은 목업 UI의 레포 통합과 사내 배포를 위한 작업이다. 계획이나 문서 작성으로 끝내지 말고 구현·검증·문서·커밋·push·PR 생성 또는 갱신까지 수행하라.

1. 시작과 구현 기준
- 최신 main, 관련 열린 PR, 로컬 변경을 확인하고 AGENTS.md와 docs/STATUS.md, 변경 대상 경로의 지침을 읽어라. 기존 유효한 승인과 변경을 보존하고, 관련 작업이 이미 있다면 중복 구현하지 마라.
- 이 문서와 같은 폴더의 ees-demo-workspace.html을 읽고 원본 화면과 동작을 확인하라. 파일이 없으면 요청에 지정된 브랜치·커밋·관련 PR을 확인하라. 원본을 보지 않고 기존 목업과 동일하다고 주장하지 마라.
- 원본은 HTML/CSS/JS가 포함된 대화용 HTML fragment다. 레포의 UI 구조와 인증·라우팅·빌드 방식에 맞게 연결하라. 이 경로의 참고 원본을 추가한 것만으로 포털 화면이 제공되지는 않는다.
- 기존 시스템에 ‘EES Work 시연’ 진입점을 추가하고, 들어가면 통합 목업 화면을 표시하라. 목업 화면의 이름은 EES Work로 한다. 최신 설계 문서와 충돌하면 사용자 합의와 실제 소스를 근거로 해결하고 중요한 차이는 기록하라.

2. 업무 실행 화면
- 왼쪽 업무 네비게이션, 중앙 대화창, 오른쪽 작업 패널을 유지하고 상단에는 클릭 가능한 현재 업무 경로를 표시하라.
- 셋업·운영·장애대응을 선택하고, 대상 시스템과 진행 중인 현장을 확인한 뒤 프로세스(P) → 태스크(T) → 잡(J)을 탐색할 수 있어야 한다. 트리 펼침과 업무 선택을 분리하고, 사이드 목록의 팝업·고정·접기를 지원하라.
- 선택한 P/T/J에 따라 오른쪽 패널의 목적·진행 상황·선행 조건·실행 항목·결과가 바뀌어야 한다. 탐색 중 기존 대화와 입력 중인 문장을 유지하라.
- 대표 셋업은 ‘신규 공장 횡전개’다. 태스크 순서는 사전준비 → AP, DB 인프라 준비 → 시스템 설치 → 각 시스템간 인터페이스 확인이다. 시스템 설치에는 설치·설정 확인, DB 연결 확인, AP 연결 확인 잡이 들어간다.
- DB 잡은 진단 경로·대상 식별·읽기 기능을, AP 잡은 네트워크·서비스·상태 API·기능 응답을 차례로 점검하는 예시를 제공하라. AP 첫 실행은 상태 API 실패와 후속 점검 미수행, 재시도는 통과로 재현한다. 이전 실패 기록도 확인할 수 있어야 한다.
- 선행 작업이 끝나지 않으면 후속 실행을 막고, 실패·미수행을 성공으로 집계하지 마라. 상위 진행률, 재실행에 따른 후속 결과 무효화, 결과 요약을 일관되게 연결하라.
- 운영과 장애대응도 원본의 대표 예시를 유지하여 메뉴가 시연 가능한 화면으로 이어지게 하라.

3. 설계 워크스페이스와 현장별 차이
- 업무 실행과 구분되는 ‘설계 워크스페이스’를 제공하라. 비개발자가 폼과 목록으로 ‘업무 절차 / 스킬·지침 / 도구 / 현장 정보’를 편집하고 오른쪽 미리보기를 확인할 수 있게 하라.
- P/T/J 추가·이름 변경·순서 변경·사용 여부·적용 조건·선행 작업·완료 기준을 편집한다. 상위 공통 지침을 상속하고, 각 단계에 스킬·지침과 허용 도구를 연결하며, 잡에는 실행 도구의 순서와 입력값을 지정한다.
- 스킬·지침 작성, AI 초안 예시, 등록 도구 선택·입력 매핑·시연 연결 상태, 도구 시험 결과를 제공하라. 새 도구 등록은 메타데이터와 모의 응답 설정이며 실제 코드나 API 구현이 완료된 것으로 표현하지 마라.
- 국가·공장·라인·인프라 재사용·시스템 간 연계 여부에 따라 절차와 입력값이 달라지는 모습을 제공하라. 미국·헝가리·한국 현장을 사용하고 헝가리의 연계 미사용 조건에 따른 잡 제외를 시연한다. 시스템별 실제 전문가 절차가 없는 부분은 예시 템플릿임을 표시하라.
- 초안 저장 → 시험 실행 → 변경 검토 → 목업 내 게시 → 새 셋업 시작을 연결하라. 게시된 새 버전은 새 셋업에 적용하고, 진행 중인 셋업의 절차·현장 조건·기존 결과는 시작 당시 버전으로 유지하라.
- 잘못된 입력 매핑, 미연결 도구, 순환 선행 조건을 시험에서 검출하고 수정하게 하라. 시험 후 수정하면 다시 시험해야 게시할 수 있어야 한다.

4. 구현 범위와 시연 상태
- 업무 실행·시험·AI 응답·도구·게시 기능은 모두 시뮬레이션이다. 실제 사내 LLM, DB/AP, Jira·Confluence·GitHub 등 업무 API를 호출하거나 실제 모델·스킬·툴·공용 설정을 등록·변경하지 마라. 화면에 ‘시연용 목업 · 실제 시스템 미연결’을 명확히 표시하라.
- 기존 로그인·인증, 대화 기록, 사용자 데이터, 모델·도구·스킬 설정과 기존 연동을 보존하라. 목업 상태는 실제 업무 데이터와 분리하고 브라우저의 목업 세션 안에서 관리하라. 새로고침 시 초기화되는 정책을 표시하고 ‘시연 초기화’로 최초 상태를 재현하라.
- 버튼·시연 채팅·E2E 테스트가 같은 액션과 상태 전이를 사용하게 하라. 목업 내부에는 실행 가능한 액션을 일관되게 정의하되 범용 워크플로 엔진이나 실제 에이전트 오케스트레이터로 확대하지 마라. 지원하는 시연 문구는 재현 가능한 모의 응답으로 처리하고 미지원 요청은 안내하라.
- ChatGPT 전용 런타임, 절대 로컬 경로, 외부 CDN·폰트·아이콘 서버에 의존하지 않게 하라. 기존 프로젝트의 로컬 자산과 구성요소를 우선 재사용하라.
- 한국어 가독성, 원본의 색상·간격·3영역 구조를 유지하고 이모지는 사용하지 마라. 1920×1080과 축소 창에서 잘림·겹침 없이 사용할 수 있게 하라. 작은 구현 결함은 바로 수정하되 새로운 디자인 탐색으로 범위를 넓히지 마라.

5. 검증
- 프로젝트의 필수 빌드·검사와 아래 핵심 시연 경로의 브라우저 E2E를 수행하라. 테스트는 가능하면 사용자 동작과 화면 결과를 기준으로 작성하라.
- 진입 → P/T/J 탐색 → DB 성공 → AP 실패·미수행 → AP 재시도 → 인터페이스 검증 → 상위 완료·결과 요약.
- 설계 수정 → 도구·스킬 연결 → 잘못된 매핑 시험 실패 → 수정·재시험 → 게시 → 새 현장에 새 버전 적용 → 기존 현장의 이전 버전·결과 유지.
- 현장별 적용 제외, 대화·작성 중 입력 유지, 팝업 재열기, 운영·장애대응 예시, 실행 중 초기화를 확인하라.
- 목업 업무 액션이 실제 업무 API를 호출하지 않는지 네트워크 요청으로 확인하라. 인증·정적 리소스 요청과 업무 실행 호출은 구분하라. 기존 일반 대화와 주요 연동 진입 화면이 깨지지 않았는지도 확인하라.
- 원본에 대한 이전 검사는 스크립트와 모의 DOM 상태 검사였다. 이를 실제 브라우저 E2E나 사내 검증으로 재사용하지 마라. 이번 커밋에서 수행한 검사만 증거로 남기고, 브라우저나 사내 환경에 접근하지 못하면 미검증 범위를 명시하라.

6. 배포와 인계
- 현재 Open WebUI + 래퍼의 빌드·패치·배포 경로를 재사용하여 사내에서 화면이 제공되도록 하라. PR만 만들고 실제 배포 경로 연결을 빠뜨리지 마라.
- 필요한 문서와 상태를 현재 문서 구조에 반영하고, 무관한 장애 수정이나 문서 전용 작업과 변경 이력을 섞지 마라. 동일 목적 PR이 있으면 재사용하고 불필요한 PR 적층을 피하라.
- 검증·커밋·push·PR 반영 후 저장소 규칙과 유효한 승인 범위에 따라 병합·배포를 진행하라. 이미 승인된 범위를 다시 묻지 마라. 새 승인이 필요한 단계가 남으면 적용 근거와 검토 가능한 변경을 제시하라.
- 사내 PC에서만 실행 가능한 단계는 현재 프로젝트의 실제 명령을 확인하여 복사·붙여넣기용 PowerShell 한 블록으로 제공하라. 적용 버전, 실행 상태, health, 목업 화면 반영 여부의 핵심 결과와 실패 시 다음 행동을 간결히 출력하게 하라. 기존 복구·재시작 보호를 재사용하고 설정값·토큰·대량 로그는 출력하지 마라.
- 최종 응답에는 변경 요약, 커밋·PR, 실제 검사 결과와 미확인 항목, 사내 적용 명령, 접속 메뉴·경로, 3~5분 시연 순서, 기존 화면으로 돌아가는 방법을 제시하라. 레포 반영 완료와 사내 배포 확인 완료를 구분하고 실제 증거가 확보된 범위까지만 완료로 보고하라.

## 원본 관리와 확인 범위

- 이 자료는 EES Work 통합 목업의 구현 담당자가 사용하는 기준 원본이다. 유지 책임은 해당 구현 작업 담당자에게 있으며, 변경 시 이 지시와 실제 목업의 관계를 함께 확인한다. 현재 작업 상태는 [STATUS](../../STATUS.md), 검증 증거는 [기존 평가 기록](../../../evals/scenarios.md#ees-work-mockup-reference-20260914)에서 관리한다.
- 최초 레포 반영 원본: 87,747 bytes, SHA-256 `802a8943870e568e58f17976f2c478470b47a6a12b30b9caec486cf008687f67`. 이는 원본 식별값이며 추후 수정본에 같은 해시를 적용하지 않는다.
- 원본은 ChatGPT 제공 Lucide 초기화를 선택적으로 사용한다. 실제 앱 통합 시 프로젝트의 로컬 아이콘·스타일 자산과 인증·라우팅·CSP·빌드 경로를 사용한다.
- 대화에서 수행한 구문·모의 DOM 상태 검사는 실제 브라우저 E2E·사내 배포 확인이 아니다. 구현한 커밋에서 해당 검증을 수행하고 실제 증거만 기록한다.
