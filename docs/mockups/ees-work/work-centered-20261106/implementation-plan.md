## 판 1 화면과 표시 상태

| 화면 ID | 가운데 화면 | 검토할 대표 내용 |
|---|---|---|
| `operations` | 업무 진행 | 단계·작업 목록, 실행 상태, 판정·결과 |
| `procedure` | 업무 절차 작성 | 단계·작업 편집, 저장·게시 상태 |
| `tools` | 도구 작성 | 연결·시험·사용 설정 |
| `documents` | Native 참고 문서 화면 | 관리 화면 진입·복귀와 오른쪽 대화 유지 |

기본 치수는 1920px에서 **256 / 1104 / 560px**, 1366px에서 **56 / 830 / 480px**다. 순서는 탐색 / 업무 / 채팅이며 목업의 기준값이다. 사용자가 조절한 폭과 작은 화면에서는 가운데 업무의 가용 폭을 먼저 계산한다. 겹쳐 열기 전환은 실제 영역 폭을 기준으로 구현하고 경계 전후를 검증한다.

- 가운데는 선택한 업무 또는 관리 화면을 유지한다. 목록·결과에는 넓은 폭을 활용하고 입력 폼은 과도하게 늘어나지 않도록 최대 폭을 둔다.
- 채팅의 열림·접힘·확대·폭 조절·겹쳐 열기 상태를 제공한다. 확대 후 복귀 시 기존 업무 선택, 스크롤, 미저장 내용을 유지한다.
- 작은 화면은 업무를 기본으로 보여 주고 채팅을 겹쳐 연다. 채팅을 닫아도 업무가 닫히거나 초기화되지 않는다.
- 새 대화·대화 기록 선택은 오른쪽 대화만 바꾼다. 가운데 업무·관리 화면을 임의로 이동하거나 미저장 내용을 지우지 않는다.
- 업무를 고르지 않아도 일반 질문을 할 수 있다. 기존 업무 선택 안내를 사용하며 별도 대시보드를 범위에 추가하지 않는다.

## 공통 연결 계약

### 화면 영역과 생명주기

1. 가운데 업무 host는 기존 `#ees-work-panel`과 `hosts().panel` 연결을 우선 재사용한다. 기존 표시·편집·이벤트 연결을 일괄 이름 변경하지 않는다.
2. Chat은 계정별로 하나의 인스턴스를 유지한다. 접기·확대·폭 변경·Native 화면 왕복 때문에 재생성하거나 대화를 복제하지 않는다. 계정 전환에 따른 기존 개인 자료 초기화와 격리는 유지한다.
3. `EesShell`의 가운데 경로와 대화 ID를 분리한다. 현재 `Chat.ready()`의 URL 제한, `hasChat`, `chatReady`, `newChat`, `adoptChat`, `shouldInitChat`을 함께 점검한다. Native 직접 진입에서도 오른쪽 대화가 준비되어야 한다.
4. 참고 문서·작업 지침·AI 도우미 설정 등 Native 관리 경로에서도 채팅을 유지한다. 새 대화나 대화 생성 완료가 가운데 경로를 `/` 또는 `/c/...`로 강제 변경하지 않도록 처리한다. 기존 권한·폴더 읽기 전용·임시 대화 조건은 각각 유지한다.
5. 키보드로 채팅 입력에 진입하면 접힌 채팅을 먼저 열고 포커스를 옮긴다. 겹쳐 열린 채팅의 닫기·Escape는 호출 버튼으로 포커스를 돌린다. 내부 메뉴·모달의 Escape 처리를 먼저 존중한다.

### 개인 표시 설정과 기존 자료

1. 기존 `selection.panel_open`·`panel_width`는 업무 패널 설정이다. **채팅 열림·폭 설정으로 재해석하지 않는다.** 예전 `panel_open=false` 때문에 가운데 업무가 사라지거나 새 채팅이 의도치 않게 닫히면 안 된다.
2. 새 채팅 표시 설정은 별도 필드로 관리한다. 구체적 필드명·기본값·저장 범위는 공통 셸 착수 전에 메인과 A가 한 곳에서 정한다. [ees_workflow_workspace.py](../../../../agent-pack/skills/ees-work-demo/scripts/ees_workflow_workspace.py)의 `action == 'save_ui'` 분기는 상태 dict를 `work_ui`에 JSON으로 저장하므로 새 표시 필드에 DB 스키마 변경은 필요하지 않다. 기존 `_revision(body, revision)` 동시 편집 보호와 `len(_dump(state)) > 40000` 크기 제한을 유지한다.
3. 대화 표시 상태 변경은 업무 저장·게시·실행 명령을 발생시키지 않는다. 기존 개인 초안·판정 선택·동시 탭의 변경을 통째로 덮어쓰지 않는다.
4. 기존 대화의 입력 텍스트·서식·첨부·진행 중 업로드·응답 스트리밍을 보존한다. 업무 실행·작성 화면의 미저장 값과 스크롤도 별도로 보존한다.

### 대화와 업무 참고

1. 채팅 입력창 가까이에 실제로 전송할 현재 업무·작업 참고를 표시한다. 보내는 순간의 참고를 메시지에 보존한다.
2. 이후 화면을 바꿔도 과거 메시지의 참고를 새 업무로 덮어쓰지 않는다. 메시지의 참고를 열면 당시 대상·실행 근거를 확인한다.
3. 공장·시스템·작업·계정 변경 후 늦게 도착한 AI 제안이 다른 대상에 적용되지 않도록 기존 문맥·요청 순서 검증을 유지한다.
4. Native 화면에 채팅이 보인다는 이유만으로 문서 본문·설정값에 새 접근 권한이 생기지 않는다. 실제로 지원하는 참고만 보내고 없는 참고를 합성하지 않는다.

## 제품 구현 단계의 메인 + 서브에이전트 5개

| 담당 | 단독 수정 범위 | 책임과 전달물 |
|---|---|---|
| 메인 | `ees-work-launcher.js`, 공통 계약·인계 문서, 통합 | 업무·대화 연결, 개인 UI 상태 저장, 담당 간 인터페이스, 통합·최종 검수 |
| A · 화면 틀·채팅 | `frontend/patches/0001-ees-native-hooks.patch` | `EesShell`·`Chat`·`Navbar`·Native 경로·상태·번역. 업무 가운데 배치, 채팅 조작과 생명주기 |
| B · 업무 실행 화면 | `branding/ees/ui/ees-work-view.js` | 넓어진 업무 진행·단계·작업·결과·판정 표시와 기존 상태 보존 |
| C · 작성 화면 | `branding/ees/ui/ees-work-designer.js` | 업무 절차·도구 작성, 목록·설정·저장·게시 표시, 미저장 내용 보존 |
| D · 공통 스타일 | `branding/ees/ui/ees-work-launcher.css`, `branding/ees/ui/chat-theme.css` | 가운데 업무의 폭·여백, 오른쪽 채팅, 공통 탭·색·글꼴, 반응형·움직임 |
| E · 검증 | 이번 변경에 직접 관련된 `tests/`와 검증 산출물 | 화면·동작·자료 보존 회귀 검사, 실제 브라우저 대조, 실패 재현과 재검증 |

`EesShell`·`Chat` 등 여러 Svelte 파일은 저장소에서 하나의 패치에 들어 있으므로 A만 그 패치를 수정한다. B·C는 필요한 CSS 선택자·상태·치수를 D에게 전달하고 공통 CSS를 직접 수정하지 않는다. 공통 상태·bridge 변경은 메인과 A가 합의한 계약으로 전달한다. 검증 담당 외 에이전트도 검사를 실행할 수 있지만 같은 검증 파일을 동시에 고치지 않는다.

각 담당은 같은 기준 커밋에서 분리한 브랜치/작업 디렉터리를 사용한다. 담당 밖 변경이 필요하면 해당 소유자에게 전달하고, 메인이 변경 묶음을 순서대로 통합한다. 한 담당이 다른 담당의 작업을 덮거나 완료 전 브랜치를 임의 병합하지 않는다.

이번 **목업 단계의 Figma 전담·HTML 전담·계약 문서 전담**은 위 제품 구현 책임표와 별개다. 목업 작업을 제품 코드 담당 변경이나 제품 구현 완료로 기록하지 않는다.

## 의존 순서와 완료 조건

1. **검토 1판 목업·공통 계약 준비:** 네 대표 화면, 기본/접힘/확대/겹쳐 열기 상태와 기준 치수를 확인한다. 사용자가 구현할 판을 선택하면 메인이 그 목업 판·커밋, Figma 위치, 각 담당의 변경 범위를 하나로 인계한다.
2. **공통 셸 최소 동작:** 메인+A+D가 업무 host·대화 ID·표시 상태·CSS 경계를 맞춘다. 가운데 업무와 오른쪽 대화, Native 왕복, 초안·첨부 보존까지 동작하는 공통 기반 커밋을 만든다. B·C는 동시에 화면별 변경안을 준비하고 E는 수락 시나리오를 준비한다.
3. **병렬 구현:** 공통 기반에서 A는 채팅 세부 동작, B는 업무 실행, C는 작성 화면, D는 공통 스타일, E는 검증을 진행한다. 메인은 launcher 연결과 개인 상태 저장을 완성한다. 미완성 공통 인터페이스를 각자 다르게 구현하지 않는다.
4. **통합·최종 검수:** 메인이 관련 변경을 합치고 E가 같은 통합 커밋의 실제 화면을 목업과 대조한다. 발견한 문제는 해당 소유자가 수정한다. 필요한 로컬 검사 후 최종 통합 head의 필수 CI와 프로그램 ZIP 검증을 수행한다. 제품 반영·사내 실행·사용자 확인은 각각 구분해 기록한다.
