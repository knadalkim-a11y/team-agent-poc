# 워크 · 도구 API 전환 구현 계획

피그마의 ‘워크 · 도구’를 제품의 공식 화면으로 구현한다. 도구에서는 서비스가 제공하는 API 명세를 관리하고, 업무 절차에서는 단계의 작업에 API와 업무 데이터를 연결한다. 첫 통합 시연은 백업 조회 API 한 건을 등록하고 작업에서 호출한 뒤 실행 기록을 다시 여는 흐름이다.

## 착수 기준

- 제품 출발점은 2026-11-13 확인한 `main`의 `d4c2f3b7e769`이다. 착수할 때 최신 main과 열린 PR을 확인해 겹치는 변경을 먼저 반영한다.
- [지정 판의 화면·동작·캡처](https://github.com/knadalkim-a11y/team-agent-poc/blob/a48438753511b13028b6c731693771e514af68fe/docs/mockups/ees-work/api-tools-20261113/README.md)를 모든 담당자가 사용한다. 설계 PR #137의 고정 커밋은 `a48438753511`이다. 제품 개발에는 한 개의 통합 브랜치를 두고, 설계 PR을 먼저 병합할 필요 없이 고정 커밋을 참조한다.
- 기존 3단 셸, 워크스페이스 진입, 절차 저장·게시, 회차·시도·판정 이력을 재사용한다. 기존 Python 도구 작성기와 등록 소스 가져오기는 코드 도구 전용이다. 현재 선행 결과 전달은 선택·확정된 `items[].id` 목록에 한정된다. API 명세 저장, 범용 필드 연결, 실제 HTTP 실행은 제품 변경이 필요하다.
- 구현 전에 사내 API 검증에 쓸 실제 서비스의 테스트 주소·허용 호출·인증 방식과 EES Web 개발 요청 경로가 제공됐는지 확인한다. 이 값이 없어도 공통 계약과 개발용 HTTP 서버로 제품 통합을 진행할 수 있다.

## 0. 먼저 고정할 공통 계약

통합 담당자가 아래의 최소 데이터 계약과 공통 예제 두 개를 첫 커밋에 둔다. A·B·C·D의 통합 순서는 계약 → 카탈로그 저장과 실행 → 목록·절차 연결이다. 공통 예제로 각 작업 브랜치를 독립 검증하며 E는 계약을 정할 때부터 참여한다. 같은 예제를 서버·화면·E2E가 사용한다. 표의 명칭은 논리 항목이며 기존 저장 구조에 맞는 필드명을 선택한다.

| 항목 | 합의할 내용 |
| --- | --- |
| 서비스와 API | 서비스의 안정적인 ID와 표시명, API의 안정적인 ID와 버전, 업무 이름·용도, HTTP 메서드·주소, 입력 정의·위치, 응답 예시·필드·형식. 서비스 이름을 바꿔도 연결이 유지된다. 공장 정보는 해당 서비스의 주소나 명세가 받는 입력에서 처리한다. |
| 작업의 연결 | 작업이 참조하는 API와 버전, 고정값·업무 문맥·실행 시 입력·확정된 앞 작업 결과 중 입력 출처, 응답 경로·배열 선택·형식. 절차 편집 초안, 게시 버전, 이미 시작한 회차의 반영 시점을 구분한다. |
| 권한과 실행 | 초기 명세 등록·편집은 기존 도구 관리자 권한을 재사용하는 안으로 잡는다. 절차 편집자의 연결 권한과 실행 계정의 서비스 권한은 각각 판정한다. 모든 서비스에 공통 인증 입력을 요구하지 않는다. 인증이 필요한 서비스는 신뢰된 서버 설정을 사용하며 인증값은 카탈로그·도우미·실행 기록에 담지 않는다. |
| 저장·충돌·호환 | 현재 revision과 request_id 규약을 재사용한다. 새 API 종류를 추가하고, 기존 코드 도구에 연결된 작업·게시본·실행 기록은 그대로 읽고 실행할 수 있게 한다. 대응 API가 확인된 작업만 명시적으로 재연결한다. |
| 공통 예제 | 사내 백업의 GET /backups는 읽기와 목록 결과를 검증한다. EMS 설비 알람은 선택된 앞 작업의 알람 코드를 다음 등록 요청에 연결한다. 두 서비스의 응답 모양을 다르게 둔다. 사내 주소나 실제 운영 데이터는 테스트에 넣지 않는다. |

## 1. 메인 1명과 병렬 담당 5명

공통 계약 커밋에서 담당별 worktree를 분기한다. 처음에는 각 담당자가 첫 시연에 필요한 부분을 먼저 전달하고, 두 번째 예제와 확장 기능을 이어서 개발한다.

| 담당 | 소유할 변경 | 첫 시연 이후의 변경 |
| --- | --- | --- |
| A · 명세 저장·가져오기 | 서비스·API·버전 조회/저장, 직접 등록, 동시 편집·재전송 처리. 기존 operations 라우트의 명령 규약에 맞춰 구현한다. | 서비스 생성·이름 변경, 제공자 OpenAPI 3.0/3.1 JSON·YAML의 URL 가져오기와 기능 선택 등록. 파일·붙여넣기는 보조 경로. 재가져오기와 필드 변경 내역을 계산한다. |
| B · HTTP 시험·실행 | 등록된 GET 호출을 수행하는 서버 어댑터, 서비스별 인증 해석, 응답 경로 추출. 기존 실행 시도·판정·기록 경로에 연결한다. | 변경 요청, 입력 위치별 인코딩, 객체·배열·빈 응답, 실패·시간 초과와 중복 처리. 효과가 불명확한 쓰기 요청은 자동 재발송하지 않는다. 서비스가 상태 확인이나 멱등 키를 제공하면 그 계약을 사용한다. |

### 충돌이 집중되는 코드

- 도구 목록 `toolsHTML()`과 작업 선택 `jobToolChoices()`, `openJobToolSetup()`이 모두 `branding/ees/ui/ees-work-designer.js`에 있다. C와 D는 자기 화면·동작을 격리하고 메인이 공용 이벤트·진입점을 연결한다. 공통 CSS도 동일한 선택자에 두 담당자가 쓰지 않도록 소유 구간을 지정한다.
- `agent-pack/skills/ees-work-demo/scripts/ees_workflow_operations.py`의 공용 명령 분기·실행 시도 경계는 메인이 연결한다. B는 HTTP 전송과 결과 해석, D는 작업 연결 저장·선행 결과의 출처와 형식 검증을 소유한다. A의 명세 비교 결과와 D의 사용처 조회 결과는 API·버전·필드 식별자로 합친다.
- `ees-work-launcher.js`와 `EesShell`은 기존 셸을 사용한다. 새 JS·Python 모듈이 생기면 메인이 `scripts/build_ees_webui.py`의 소스 조립·배포 파일 목록을 함께 반영한다. 단위 시험만 통과하고 wheel에서 모듈이 빠지는 경우를 잡는다.
- 각 담당자는 해당 단위·계약 시험을 맡고, E는 독립된 실제 제품 E2E와 시각 검수를 맡는다. 작업마다 전체 배포 파이프라인을 돌리는 대신 변경된 시험을 먼저 실행하고 최신 main과 합친 최종 제품 커밋에서 전체 필수 CI를 실행한다.

## 2. 통합 순서와 단계별 완료 조건

| 순서 | 실제 제품에서 보여 줄 결과 | 완료 조건 |
| --- | --- | --- |
| ① 작동하는 조회 한 건 | 워크 · 도구에서 ‘백업 결과 조회’를 직접 등록 → 새로고침 → 절차의 단계·작업에서 연결 저장 → 회차 시작 → 실제 테스트 HTTP 서버 호출 → 결과·이력 재열기 | URL·입력이 맞는 요청이 서버에 1회 도착하고, 해당 서버가 보낸 응답이 저장된 명세에 따라 화면에 표시된다. 잘못된 주소나 응답은 실패로 표시된다. |
| ② 작업 사이 결과 전달 | 설비 번호로 알람 조회 → 한 건 선택 → 다음 작업의 등록 API에 알람 코드 전달 | 선택한 행·필드가 명세에 지정한 위치에 전달된다. 같은 회차의 최신 확정 결과를 사용한다. 값 누락·형식 불일치·미선택 상태를 화면에서 바로 구분한다. 쓰기 요청이 중복되거나 결과 미확인 상태에서 성공으로 기록되지 않는다. |
| ③ 서비스 운영과 변경 | 서비스 추가·이름 변경, URL 명세의 일부 기능 등록, 파일·붙여넣기, 변경 영향 확인과 재연결 | 같은 원본을 재등록해도 중복되지 않는다. 예를 들어 등록된 결과 필드 `code`가 `alarmCode`로 바뀌면 영향받는 작업과 입력을 보여 준다. 필요한 수정 권한을 확인하고 revision이 모두 일치할 때 명세와 관련 편집본을 함께 적용한다. 취소·충돌 시 부분 변경이 없고 기존 게시본·회차 기록을 보존한다. 사용 중단 예정과 실제 철회 상태도 구분한다. |
| ④ 제품 비교·배포 준비 | 실제 제품 화면과 지정 판의 동일 상태를 비교하고 설치 산출물로 첫 시연을 재현 | Figma 6개 화면의 차이를 확인·수정하고 단위·계약·Native·Linux/Windows 필수 CI를 확인한다. 패키지 검증과 사내 테스트 시스템에서의 인증·실행 확인은 별도로 기록한다. |

## 3. 효율을 좌우하는 검수

- **픽셀 대조**는 1920 × 1080, 좌측 256 / 중앙 1104 / 도우미 560px, 메뉴·도우미 펼침 상태로 고정한다. 6개는 목록, 빈 등록, 작성 중 등록, 편집, 작업 연결 전, 결과 전달 연결 후다. 폼 960px, 편집 저장 버튼 상단 오른쪽, 목록의 메서드·경로·업무명 순서를 DOM 측정과 겹친 화면으로 확인한다. 기존 1048px 비교 기준을 이 화면에 적용하지 않는다. 나머지 URL 등록·변경 영향·실행 화면은 동작 시험과 해당 Figma 프레임의 상태별 검토로 보완한다.
- **비개발자 흐름**에서 신규 등록은 가운데의 빈 양식으로 시작한다. 등록 방식 탭 전환, 도우미 열기·닫기, 취소 시 작성 내용과 출발한 작업을 보존한다. 작업에서 신규 등록 후 돌아오면 해당 API를 선택해 두고 연결 저장에서 관계를 확정한다. API별 대상 공장 선택과 일괄 인증 연결 단계를 만들지 않는다.
- **데이터·실행**은 서비스 이름 변경, 두 가지 서로 다른 응답 형식, 빈 결과, 권한 철회, 잘못된 HTTP 응답, 쓰기 타임아웃, 동시 수정과 중복 클릭을 검증한다. 기존 코드 도구가 연결된 게시 절차, 이미 시작한 회차와 과거 판정도 다시 연다. 개발용 HTTP 서버 호출 성공과 사내 실제 서비스 호출 성공을 따로 기록한다.
- **시험 연결**은 기존 `tests/test_ees_work_authoring_ui.cjs`, `tests/test_ees_work_figma_authoring_native.py`, `tests/test_ees_work_operations.py`, `tests/test_ees_work_workspace.py`, `tests/test_ees_tool_runtime_native.py`를 활용한다. 새 시험은 해당 delivery suite에 등록하고 `python tests/ees_delivery_suite.py --audit --output dist/ees-delivery-coverage`로 누락을 확인한다.

계획 수립 시점에 확인한 범위는 지정 설계, 현재 코드 경계, 기존 시험 및 배포 경로다. 제품 실행 결과와 시각 일치 판정은 각 통합 단계의 산출물이다.
