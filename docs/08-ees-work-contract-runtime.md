# EES Work — P/T/J Contract와 최소 실행 Runtime 설계

설계 기준일: 2026-09-16. **목표 설계이며 기능 구현·사내 적용 완료를 뜻하지 않는다.**

## 문서의 역할

이 문서는 업무 작성 규격, Runtime POC의 경계, 장기 확장의 관리 원본이다. 일시적인 대화 요약이나 배포 인계서로 사용하지 않는다. 후속 개발자는 이 문서를 갱신하며 같은 주제의 설계본을 매 세션 새로 만들지 않는다.

- **현재 작업·실제 적용:** [STATUS](STATUS.md). Git 준비, 사용자 보고, 미확인을 여기에서 구분한다.
- **기존 화면·공동 작업 합의:** [EES Work 작업 지시](mockups/ees-work/TASK.md). 기존 UI·권한·공동 작업 목표를 폐기하지 않는다.
- **이 설계의 수락 기준·검토 기록:** [Runtime POC 평가](../evals/ees-work-runtime-poc.md). 기존 시험 결과는 [기존 평가표](../evals/scenarios.md)에 그대로 둔다.

이번 대화에서 합의한 중심축은 P/T/J 3단계, 최소 Contract, 의미와 실행의 분리, 실제 도구 결과에 근거한 J 판정이다. 아래의 판정 세부사항·동시 실행 제한·단계별 이행은 **이번 재검토에서 구체화한 제안**이다. 문서 반영은 해당 코드 변경·병합·배포나 신규 권한의 승인이 아니다.

## 1. 제품 목표와 유지할 구조

> 사람이 이해할 수 있는 업무 구조를 표준화하고, 사람과 AI가 같은 업무를 작성·수행·검증하며, 검증 근거를 이용해 업무 방식 자체를 점진적으로 개선한다.

사람이 탐색하는 업무 계층은 **Process → Task → Job** 세 단계로 유지한다. 공장·시스템·업무 분류는 탐색 조건이며 새로운 실행 계층으로 늘리지 않는다. Step·Action·Check는 J 내부 수행 세부사항 또는 실행 순서 표시이지 별도 업무 계층이 아니다.

| 계층 | 담당하는 의미 | 일상 업무 패널 |
|---|---|---|
| P — Process | 최종 업무 목표와 범위 | 하위 T 진행·남은 업무·전체 결과 |
| T — Task | 의미 있는 업무 단계 | 하위 J 상태·선행 대기·다음 행동 |
| J — Job | 독립적으로 수행하고 결과를 확인하는 업무 단위 | 입력·수행·완료 기준별 판정·근거 |

J의 내부 도구 호출마다 새 J를 만들지 않는다. 별도 사용자 승인·책임·결과 전달·재시작 경계가 필요한 경우에는 여러 J로 나누는 것을 검토한다. 거대한 J에 모든 일을 숨기거나 재사용만을 이유로 업무 계층을 늘리지 않는다.

Workspace는 **업무 정의를 작성하는 곳**, 업무 패널은 **특정 진행 건을 수행하는 곳**, 채팅은 **같은 정의·진행 건을 이해하고 조작하는 자연어 창구**다. UI와 AI는 같은 서버 Action·권한·revision 검사·결과 저장을 사용한다. AI에게만 허용된 우회 쓰기 경로를 만들지 않는다.

## 2. 최소 Contract: 작성 부담은 작게, 의미는 명확하게

Contract는 실행 전의 업무 정의다. 실제 입력값·현재 판정·소요시간은 Contract에 쓰지 않는다.

| 항목 | P | T | J |
|---|---|---|---|
| 이름 | 필수 | 필수 | 필수 |
| 목표 / 목적 | 업무 목표 한 문장 | 단계 목적 한 문장 | 작업 목표 한 문장 |
| 완료 기준 | 업무 결과에 관한 문장 목록 | 단계 결과에 관한 문장 목록 | 실제 확인할 결과에 관한 문장 목록 |
| 수행 정의 | 하위 T 구성 | 하위 J 구성 | 사람 확인 / 초안 작성 후 검토 / 승인 도구 실행 |
| 조건·연결 | 적용 조건, 업무별 제약 | 적용 조건, 선행 작업 | 필요한 입력 정의, 적용 조건, 선행 작업, 수행 지침·자산 |

이름·목표/목적·완료 기준은 게시 전에 필요하다. J의 수행 정의도 필요하다. 상세 항목은 무조건 선택이라는 뜻이 아니라 **선택한 수행 방식이 요구할 때 필수**다. 예를 들어 입력 없는 수동 확인에는 입력 Schema가 불필요하지만, 대상 ID를 요구하는 자동 점검에는 대상 입력의 공급 경로가 필요하다.

시스템이 관리할 ID·규격 버전·게시 revision·작성 출처는 사용자가 반복 입력하지 않는다. 추가 제약을 작성하지 않아도 공통 실행 정책은 계속 적용되며 하위 업무나 AI가 완화할 수 없다.

사용자에게는 `무엇을 위한 업무인가요?`, `무엇이 확인되면 끝인가요?`, `어떻게 수행하나요?`를 보여준다. 도구·스킬·검증 연결은 상세 설정으로 제공하되 미연결·권한 부족·현재 실행 불가는 기본 화면에서도 숨기지 않는다. 초안에서는 미완성을 허용하고, 게시와 실제 실행에서 필요한 조건을 강제한다.

## 3. 완료 기준과 실제 판정을 연결하는 방법

### 3.1 네 가지 책임을 구분한다

| 개념 | 질문 | 예시 |
|---|---|---|
| Goal / Purpose | 왜 이 일을 하는가? | AP의 업무 사용 가능 상태를 확인한다. |
| Outcome Criteria | 어떤 상태를 확인해야 하는가? | 승인된 주요 기능 시험이 기대 결과와 일치한다. |
| Execution Definition | 무엇을 수행하고 어떤 방법으로 검증하는가? | 승인된 점검 함수를 실행하고 검증 결과를 기준 ID에 연결한다. |
| Completion Policy | 언제 완료로 집계하는가? | J의 필수 기준이 모두 유효하게 충족되었을 때 |

Completion Policy는 v1에서 서버의 고정 규칙으로 둔다. 사용자가 AND/OR·가중치·임의 식을 편집하는 Rule Engine을 만들지 않는다.

### 3.2 Criterion은 작게 유지한다

```yaml
outcome_criteria:
  - id: health-ready
    text: 지정한 대상의 Health 점검이 승인된 정상 조건을 만족한다.
```

위 표기는 **논리 모델 예시이며 현재 API가 받아들이는 payload가 아니다.** Criterion은 안정적인 `id`와 `text`를 기본으로 한다. ID를 화면상의 순번과 같게 취급하지 않는다. 정렬만 바뀌면 동일 ID를 유지하고, 기준 의미 변경은 새 정의 버전으로 관리한다.

기준은 행동 목록보다 확인할 상태로 쓴다. `점검을 수행한다`보다 `점검 결과가 승인된 기준과 일치한다`가 적합하다. 자연어 표현의 품질은 초기에는 AI/업무 담당자 검토 대상이며 단순한 문장 패턴 검사로 내용의 타당성을 보장하지 않는다.

숫자 기준을 업무에서 금지하지 않는다. 필요한 임계값·기대 버전·대상 범위는 승인된 점검 명세/검증 함수에 명확히 둔다. Criterion 편집기에 범용 수식 언어를 넣지 않는 것과 검증 코드에 구체적인 비교 조건을 두는 것은 다르다.

### 3.3 Verification Binding은 수행 정의에 둔다

```text
완료 기준                     수행 정의의 검증 연결
health-ready  ← 승인된 Health 검증 함수의 health_ready 체크
feature-ready ← 승인된 기능 검증 함수의 feature_ready 체크
```

`어떤 실행 단계 / 어떤 버전의 검증기 / 어떤 체크 결과가 / 어느 Criterion을 판정하는지`를 게시 정의의 일부로 고정한다. 판정과 관측값은 실행 기록에만 저장한다. 검증 경로를 Criterion 본문에 하드코딩하지 않되, **검증 연결까지 실행 시 AI가 임의 추론하도록 비워두지는 않는다.**

한 도구가 여러 기준을 평가할 수 있고, 여러 점검 결과를 한 기준의 검증기가 종합할 수도 있다. POC에서는 명시적인 소수의 체크 연결과 필요할 때의 작은 검증 함수만 사용한다. 다대다 매핑 편집기나 범용 조건 언어는 만들지 않는다.

자동 판정할 J의 각 필수 기준에는 승인된 검증 경로가 있어야 한다. 없으면 `검증 연결 필요`로 표시하고 자동 완료하지 않는다. 실제 연결이 없는 정의의 보관·검토는 가능하지만 실행 준비가 끝났다고 표현하지 않는다. 사람 확인을 쓰려면 게시된 수행 정의에서 명시해야 하며 오류 시 임의로 수동 성공으로 바꾸지 않는다.

### 3.4 실행 성공과 업무 기준 충족은 다르다

```text
승인된 실행 요청
 → Tool/코드 실행 결과
 → 응답 형식·대상·완전성 확인
 → 기준별 검증
 → 판정 + 근거 저장
 → J 상태 집계
```

HTTP 200이나 예외 없이 함수가 끝난 것만으로 Health 정상·업무 목표 충족을 판정하지 않는다. 승인된 검증기가 대상·응답 내용·필수 항목을 확인해야 한다. 조회 0건도 검색 범위·페이지 처리·권한·완전성이 확인되기 전에는 `이상 없음`의 증거가 아니다.

| 평가 상태 — 목표 표기 | 의미 | 자동 완료 |
|---|---|---|
| 충족 / PASS | 유효한 근거로 기준을 만족함 | 다른 필수 기준도 충족하면 가능 |
| 미충족 / FAIL | 유효한 관측이 기준 위반을 확인함 | 불가 |
| 미확인 / UNKNOWN | 시간초과·권한 문제·응답 누락·판정 연결 없음 등으로 판정 불가 | 불가 |
| 미평가 | 아직 수행하지 않음 | 불가 |

실행 오류 원인과 Criterion 판정은 함께 보존한다. 타임아웃은 해당 계약이 응답기한 자체를 기준으로 정한 경우에만 그 기준의 FAIL 근거가 될 수 있다. 그렇지 않으면 연결 오류로 UNKNOWN을 남기며 대상 업무의 이상을 확정하지 않는다.

사람 확인에는 **실제 확인자의 신원·대상 진행 건·정의/결과 버전·시각·확인 내용**을 연결한다. AI가 `confirm=true`를 만들었다는 사실만으로 사람 승인 증거를 만들지 않는다. 승인 버튼과 자연어 승인은 같은 권한 경계를 따르되 별도 승인 의사를 확인하는 사용자 인터랙션을 거친다. AI 초안 생성 성공과 사람 검토 완료도 분리한다.

## 4. 업무 트리와 실행 관계

P/T/J는 포함 관계이고 Dependency는 선행 관계다. Step 번호·화면상 정렬은 실행 제약이 아니다.

```text
             ┌→ J-B DB 점검 ──┐
J-A 준비 확인                 ├→ J-D 결과 취합
             └→ J-C AP 점검 ──┘
```

시스템은 선행관계에서 실행 후보와 표시용 Step을 계산한다. 다만 **Dependency가 없다는 것은 순서상 준비가 되었다는 뜻이지 안전한 동시 실행을 보장하지 않는다.** 실행 시 입력·권한·도구 사용 가능·공유 자원 충돌·동시 실행 한도를 추가 확인한다. POC는 순차 실행을 기본으로 해도 되며, 실제 동시 실행은 확인된 독립 읽기 작업에 한정한다.

계산된 Step을 강제적인 전체 대기 구간으로 사용하지 않는다. 독립 분기의 실패·사람 확인 대기 때문에 의존하지 않는 다른 작업까지 모두 멈출 필요는 없다. 반대로 선행 결과가 필요한 작업은 계속 대기한다. 도구 호출 순서·J 내부 구현 세부는 수행 정의에 둔다.

기본 작성 UX는 `T → 같은 P의 T`, `J → 같은 T의 J`를 우선 추천한다. 그러나 현재 정의에는 다른 T의 J를 참조하는 선행관계가 이미 있다. **이를 이번 문서로 금지하거나 T 전체 대기로 자동 치환하지 않는다.** 부분 결과 전달·병렬성의 의미가 바뀔 수 있으므로 기존 관계를 보존하고, 새 편집 제한은 실제 사례와 호환 검토 후 결정한다. v1에서 프로세스 간 실행 의존·동적 순환 그래프를 확대하지 않는다.

Dependency / Applicability / Completion은 각각 `언제 시작 가능한가`, `이번 건의 대상인가`, `어떤 결과이면 끝인가`다. 적용 조건의 판단 불가는 적용 제외가 아니다. 조건으로 제외된 선행 작업이 후속 입력/근거를 공급해야 한다면 후속은 미충족 상태로 남기며, 제외를 PASS 출력처럼 전달하지 않는다.

## 5. J 판정과 P/T 집계의 의미

J는 적용 대상 필수 기준을 모두 유효하게 충족하고 필요한 사람 확인이 남아 있지 않을 때 완료한다. 미확인·미평가·미연결을 PASS로 간주하지 않는다. 조건부 작업은 가능하면 J의 적용 조건으로 분리하고, 기준별 임의 조건식은 POC에서 도입하지 않는다.

T와 P는 **적용 대상 하위 업무의 절차 완료 상태**를 집계한다. 적용 대상이 0개이면 `적용 제외`이며 전체 통과가 아니다. 진행률의 분모는 적용 대상 업무 수이며 시간 절감률·자동화율이 아니다.

**하위 완료 = 상위 Outcome의 자동 증명은 아니다.** P/T의 Outcome Criteria는 의미 계약이며 하위 작업이 충분히 커버하는지는 업무 담당자와 AI 검토의 대상이다. 명시적인 검증 근거 없이 P/T의 각 기준에 PASS 배지를 붙이지 않는다. POC 화면에서는 `절차 완료`와 `상위 목표 확인`을 구분한다. 업무상 최종 인수가 필요하면 근거 검토·담당자 확인 J를 실제 절차에 둔다. 형식적인 승인 J를 모든 업무에 중복 추가하지 않는다.

상위 기준 중 조건부 항목은 적용 대상 범위를 함께 서술한다. 예를 들어 `적용 대상 인터페이스의 점검이 완료되었다`로 쓰며, 인터페이스 없는 건을 `인터페이스 정상`으로 주장하지 않는다. 향후 상위 기준별 명시적 검증 매핑은 별도 확장이다.

<a id="lifecycle"></a>

## 6. 작성·검증·게시·실행 생명주기

```text
직접 작성 / AI 제안 / 기존 절차 복제
 → Draft
 → 서버 구조 검증 + 담당자 검토 (AI 의미 검토는 보조)
 → 게시된 정의 버전
 → 진행 건 생성
 → 실행 직전 검사
 → 실행·판정·근거 저장
 → 재시도 또는 절차 완료
```

**구조 검증 — 게시 Hard Gate:** 계층, 필수 필드/기준 ID, 존재하지 않는 참조, 순환 의존, 수행 방식과 필요한 입력 연결 등 기계적으로 확인 가능한 조건을 검사한다. AI·UI·가져오기 경로 모두 같은 검사를 거친다. `id + text`가 있다는 사실만으로 기준의 의미가 충분하다고 주장하지 않는다.

**의미 검토 — 초기에는 조언:** 누락·중복·상위 목표 커버리지·불필요한 순서 등을 제안한다. AI 호출 실패나 AI의 모호한 점수만으로 게시를 금지하지 않는다. 정책 위반과 권한 검사는 조언이 아니라 별도의 서버 통제다.

**실행 검사 — 실행 Hard Gate:** 현재 사용자와 역할, 적용 조건, 입력, 선행 상태, 승인·도구/검증기 버전과 가용성을 확인한다. 게시 완료와 현재 실행 가능은 다르다. AI가 게시·권한 승인·판정 규칙 변경을 스스로 승인하지 않는다.

게시된 정의 버전에 Criterion·수행 정의·검증 연결을 포함해 진행 건을 고정한다. 기존 진행 건을 새 규격으로 조용히 바꾸지 않는다. 그러나 버전 고정이 이후의 권한 철회·정책 강화까지 무시한다는 뜻은 아니다. 자산 내용/버전이 달라지면 재검증하거나 실행을 멈추며 현재 권한을 다시 확인한다.

## 7. 실행 기록과 레퍼런스

| 관리 대상 | 내용 |
|---|---|
| Contract / Execution Definition | 목표·기준·조건·수행 방법·검증 연결의 버전 고정 정의 |
| Execution Record | 진행 건·J·시도 ID, 실제 입력의 안전한 표현, 실행/검증 버전, 기준별 판정, 오류 원인, 시각, 실제 사람 확인 |
| Evidence | 판정을 뒷받침하는 관측·검증 결과·승인 기록. 한 번의 실행에도 존재함 |
| 파생 평가·통계 | 여러 실행의 실패율·시간·사람 수정·후속 결과. 대상 수·환경·버전·측정 범위와 함께 계산 |

입력·기준·검증 연결이 바뀌면 이전 결과는 현재 완료 근거에서 제외하되 원래 시도 이력은 보존한다. 늦게 도착한 이전 시도의 응답이 새 결과를 덮지 못하게 한다. 소요시간·임계 경로·자동화율은 측정값과 정의가 있을 때만 계산하며 초기 임의 신뢰 점수는 만들지 않는다.

실제 PAT·키·사내 주소·개인 대화·업무 데이터는 이 Git 저장소에 올리지 않는다. 근거는 승인된 내부 저장소에서 최소화·접근 제어·보존 기간을 적용한다. AI 학습용이라고 모든 원문을 수집하지 않는다. Git 밖의 UI 작성 도구·스킬·모델·개인 설정도 보존한다.

레퍼런스는 `초안`, `규격 검증`, `실환경 사용 근거 있음`을 구분해 검색·활용한다. 게시만으로 신뢰 자산으로 승격하지 않는다. 실패·사람 수정 기록도 개선 분석의 입력으로 보존하되 검증된 성공 사례로 제시하지 않는다. 기록 축적은 검색·재사용을 가능하게 하는 것이며 모델 가중치가 자동으로 학습된다는 뜻은 아니다.

## 8. Runtime POC의 종료선

> 실제 반복 업무 하나에서 표준 작성 → 게시 → 실제 승인된 읽기 실행 → Criterion 판정 → Evidence → P/T 진행 → UI/AI 동일 경로를 끝까지 확인한다.

| POC에 포함 | 구현 깊이 |
|---|---|
| Contract 작성 | P/T/J 최소 항목, 기준 목록, 직접 작성·AI 제안 모두 같은 Draft 규격 |
| 구조·의미 검토 | 서버의 확정 검사, 가벼운 AI 조언. AI 검토 고도화가 실제 실행의 선행조건은 아님 |
| 실행 관계 | Dependency 기반 준비 상태·대기 사유·표시용 Step. 실제 병렬 실행은 제한적 |
| 작은 Runtime | 승인된 도구/검증기만 연결하는 실행 경계. 수동·초안 검토·도구 방식 유지 |
| 실제 도구 | 실제 승인된 읽기 경로 1개 이상. 가능하면 성격이 다른 2개 J에서 확인 |
| 검증 연결 | 기준 ID ↔ 승인된 체크 결과. 미연결·불완전 결과는 완료 차단 |
| 실패·이력 | 미확인/미충족 구분, 입력 보완·명시적 재시도·무효화·버전 고정 |
| UI/AI | 같은 업무 조회·Action·권한·결과. 사람 승인 위임 금지 |
| 사용성·측정 | 담당자가 입력·결과·오류 뒤 다음 행동을 이해하고 원문 근거와 대조 |

범용 SQL/Python/Shell 실행기, 임의 업로드 코드 실행, 모든 Tool 자동 호출, 분산 큐·스케줄러·장기 자동 재개, 업무 쓰기/발행, 자동 Tool 생성·설치, Workflow DSL, 상위 Criterion 정교한 매핑, 자동 최적화/승격은 이번 Runtime POC 밖이다.

범용성은 아무 코드나 실행하는 기능이 아니라 **업무별 처리와 공통 실행/판정/보존 규칙을 분리해 다음 업무를 추가할 수 있는 성질**이다. 하나의 업무 성공은 해당 경로의 검증이지 모든 업무에 대한 범용성의 증명은 아니다.

### 최소 실행 경계

POC 실행 요청은 진행 건·J·정의 revision·입력과 재요청 식별자를 구분한다. 결과는 실행 상태·기준별 체크·근거 참조·오류 원인을 구분한다. 구체적인 필드명과 API는 대표 J를 확정한 뒤 정한다.

UI 재클릭·AI 재호출에 같은 시도가 중복 실행되지 않게 서버에서 보호한다. 외부 I/O 전체를 SQLite 쓰기 트랜잭션 안에 넣지 않고 `실행권 확보 → 외부 실행 → revision/시도 일치 확인 후 결과 저장`으로 나누는 것을 구현 설계에서 검토한다. 이는 단일 프로세스의 작은 보호 범위이며 분산 엔진 도입 요구가 아니다.

중단·타임아웃·프로세스 종료 뒤 결과를 모르면 미확인으로 보존한다. 자동으로 완료하거나 무조건 재실행하지 않는다. 초기 읽기 작업은 명시적인 재시도로 복구할 수 있게 하고, 향후 쓰기 업무에는 별도 중복 실행·보상·확정 결과 확인 계약이 필요하다.

## 9. 대표 업무 선택과 개발 순서

현재 예시 셋업 트리는 실제 실무 절차의 확정본이 아니다. 실환경 DB/AP 진단 도구가 준비되었다고 가정하지 않는다. 첫 업무는 **실제로 반복되고, 승인된 읽기 경로와 원문 정답 대조가 가능한 것**으로 선택한다.

후보 예시는 `횡전개 사전 자료 점검`이다. 범위 확인 → 승인 문서/이슈/PR 근거 조회 → 결과 초안 → 담당자 확인의 흐름에서 이미 연결된 Confluence·Jira·GitHub 중 실제 필요한 도구를 우선 검토한다. API 호출 성공을 문서 내용의 정확성·배포 적합성으로 과장하지 않는다. 이것은 후보이며 아직 업무·대상·판정 명세를 선정했다는 뜻이 아니다.

| 순서 | 이번에 닫을 사용자 흐름 |
|---|---|
| A | 대표 P와 첫 실제 J의 입력·도구·관측 결과·판정 기준·정답 대조 방법 확정 |
| B | 그 업무의 최소 Contract 작성/게시와 기존 자료를 보존하는 호환 처리 |
| C | 첫 실제 Tool → 기준별 판정 → Evidence → J 상태·이력 연결 |
| D | 수동/초안 검토·선행 대기·P/T 집계·UI/AI 동등성까지 한 P를 완결 |
| E | 실패·재시도·권한·자료 보존·사용성·실제 업무 효과를 수락 기준으로 점검 |

아직 미수신인 기존 패널 시험 적용 보고와 이 새 개발 계획을 구분한다. 정상 서버에 과거 진단을 다시 반복하지 않는다. 기존 공장 1개·시스템 1개·P 1개·참여자 2~3명 공동 작업 목표는 유지하되, **공동 Case 편집은 이번 단일 사용자 Runtime 검증과 별도 후속 설계**로 둔다. 공동 작업 구현 전 단일 사용자 결과를 공유 기능의 수락으로 확대하지 않는다.

## 10. 장기 확장과 진입 조건

| 단계 | 확장 | 다음 단계로 갈 근거 |
|---|---|---|
| 실제 Runtime POC | 한 업무의 실제 읽기 실행·판정·이력 | [수락 기준](../evals/ees-work-runtime-poc.md#acceptance)의 해당 범위를 실제로 확인 |
| 반복 적용·재사용 | 두 번째 다른 업무, 기존 도구/스킬 재조합 | 같은 공통 규격을 재사용했는지, 업무별 예외가 Kernel에 쌓이지 않는지 검토 |
| 공동 업무 | 참여·역할·개인 대화/선택 분리·충돌·이어가기 | 기존 2~3명 파일럿의 권한·동시성·사용성 별도 수락 |
| 자동화 확장 | 추가 승인 어댑터, 제한 병렬성, 필요한 장기 작업/쓰기 경로 | 실측 병목과 업무 필요, 권한·중복·복구 계약, 별도 변경 승인 |
| AI 설계·자산 제작 | 기존 P/T/J·Skill 재사용, 지침 초안, 필요한 Tool/검증 코드 후보 | 명세·격리 시험·골든셋·코드 검토·승인 배포. 코드 생성과 실행 권한은 별개 |
| AI 업무 개선 | 신규 J 발견·병합/분리·순서/조건 개선·새 P 후보 | 실패 포함 버전별 실행 근거, 비교 가능한 기준선, 제한된 시험 적용 |

AI는 목표·지침·도구 후보를 만들 수 있도록 확장하되 자기 제안의 성공 조건을 임의로 낮추어 통과시키지 못한다. 독립된 정답 사례·검증 코드·담당자의 업무 기준을 사용한다. 과거 이력 재생/Shadow 검토는 후보 선별 근거이며 운영 개선의 인과적 증명이 아니다.

`더 좋은 업무`는 실행 속도만으로 결정하지 않는다. 품질·누락·재작업·사람 투입·위험의 기준선과 지켜야 할 정책을 먼저 둔다. 작은 POC에서 거대한 최적화 필드를 필수화하지 않고, 비교 실험이 필요할 때 별도 평가 설정으로 관리한다. 승인 축소는 AI 효율화 제안만으로 시행하지 않는다.

| 결과 | J 상태·입력·시도 이력·후속 무효화 | 체크와 Criterion의 대응, 미확인/실패 의미, 실제 근거 연결 |
| UI/AI | 같은 업무 서비스의 조회/Action 기반 | 새 판정·작성 규격의 양쪽 동일 수락 |

근거: [정의 검증](../agent-pack/skills/ees-work-demo/scripts/ees_workflow_definition.py), [업무 서비스](../agent-pack/skills/ees-work-demo/scripts/ees_workflow.py), [상태 계산](../agent-pack/skills/ees-work-demo/scripts/ees_workflow_view.py), [작성 UI](../branding/ees/ui/ees-work-designer.js).

`rule`을 여러 기준으로 나누는 것은 단순 라벨 변경만이 아니다. 기준 ID·검증 연결·이력 의미·이전 프로그램 읽기 가능성을 함께 설계한다. 기존 `rule`과 정의/진행 건을 보존하고, 자동 분할을 확정된 의미 변환으로 간주하지 않는다. 기존 성공 이력에 새 Criterion의 PASS를 소급 생성하지 않는다.

과도한 일괄 migration, 기존 Cross-Task 의존 금지, UI 자산 재등록, DB·키 재생성은 하지 않는다. 구버전 정의는 기존 읽기·이력 경로를 유지하고 새 규격으로 게시할 때 명시적으로 검토한다. 프로그램 Restore는 사용자 데이터 migration의 원복과 다르다. 구체적인 호환 방식은 구현 전 수락 사례로 검증한다.

## 12. 이번 재검토로 명확해진 사항

- `Criterion = id + text`만으로 자동 판정은 불가능하다. 실행 정의에 승인된 검증 연결이 필요하다.
- Outcome 의미와 Runtime 완료 집계는 다르다. P/T 절차 완료를 업무 목표의 자동 증명으로 표시하지 않는다.
- HTTP 200·실행 성공·타임아웃과 Criterion의 충족/미충족/미확인은 별개다.
- 선행조건 기반 준비와 안전한 병렬 실행은 다르다. 표시 Step을 강제 대기 장벽으로 사용하지 않는다.
- 같은 계층 의존은 작성 기본값이지 기존 Cross-Task 의존을 금지하는 migration 결정이 아니다.
- 게시된 정의, 실제 실행 준비, 실환경 검증, 신뢰할 레퍼런스는 서로 다른 상태다.
- Evidence는 개별 판정의 근거이고 성공률 등은 파생 통계다. 실패 기록도 학습·개선 분석에 남긴다.
- 문서·목업·코드·시험·사내 수락을 별개로 기록한다. 설명용 HTML은 동작 증거가 아니다.

추가 구조를 확정하기 전에 필요한 결정은 **대표 업무와 첫 실제 J**, 승인된 도구·검증기, 기대 결과/정답 사례, 사람 확인 범위다. 범용 엔진과 상세 DSL을 먼저 설계하지 않는다.

### 외부 원리 확인 — 프로젝트 구현을 의미하지 않음

[Python 3.11 graphlib](https://docs.python.org/3.11/library/graphlib.html)는 선행 처리에 따른 준비 노드 계산과 실행 완료 통지를 구분한다. 이 설계는 여기에 별도 업무 권한·자원 제약을 추가해 실행 가능을 판단한다.

[JSON Schema annotations](https://json-schema.org/understanding-json-schema/reference/annotations)는 설명용 주석과 validation을 구분한다. 따라서 자연어 설명이나 규격의 형식 검증만으로 업무적 정확성이 확인됐다고 보지 않는다. 두 자료는 개념 검토의 참고이며 새 의존성·런타임 교체를 요구하지 않는다.
